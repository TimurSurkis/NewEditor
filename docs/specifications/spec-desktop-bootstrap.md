# Каркас десктопного приложения P1

Статус: **решения для реализации P1 зафиксированы; результаты проверок — в трекере**.
Дата: 2026-11-24.
Основание: [архитектура](spec-architecture.md), [контракты](spec-module-contracts.md), [план](../trackers/plan-desktop-v1.md).

## 1. Границы этапа

P1 создаёт запускаемый каркас, а не редактор. В окне показываются название, отсутствие открытых документов, версия приложения и состояние служебной БД. Команды работы с документами пока не имитируются. Ядро, порты и каталоги форматов получают публичные точки входа; реализация модели следует в P2.

Один npm-проект, точные прямые версии и lockfile. Используем установленный Node.js 24.11.1/npm 11.6.2. TypeScript 6.0.3 вместо первоначально выбранного 7.0.2: typescript-eslint 8.74.0 поддерживает версии `<6.1.0`. Это техническая корректировка без изменения контрактов P0. Библиотеки редакторов и кодировок добавляются на соответствующих этапах.

## 2. Процессы и безопасность

- `main` открывает одно окно, удерживает single-instance lock, владеет SQLite. Повторный запуск активирует существующее окно. Передача файлов реализуется с выдачей ресурсов в P4/P5, без чтения произвольных путей в P1.
- `preload` собирается в CommonJS для sandbox. API `window.desktop` содержит только `getAppInfo()` и `getStorageHealth()`. Универсальных invoke/send, SQL и файлового API нет.
- `renderer` подключает React UI и передаёт ему диагностические функции через props; UI не импортирует платформу.
- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`. Запрещены новые окна, навигация с исходной страницы, webview и выдача разрешений. IPC допускает только главный frame доверенного окна с точным URL и единственным аргументом `null`.
- В production CSP запрещает сеть и inline script. В dev разрешены локальный Vite, его WebSocket и inline script/style для React Refresh и CSS HMR; окно загружает только loopback-URL Vite. Упакованное приложение игнорирует переменную dev-URL.
- Ошибки IPC возвращаются как данные без stack trace или путей. Отказ SQLite не скрывается: UI показывает ошибку, окно остаётся доступным.
- При выходе соединение БД закрывается. Неизвестная более новая схема не изменяется и выдаёт ошибку.

## 3. Служебная SQLite

База `service.sqlite` находится в `app.getPath('userData')`. Для изолированных проверок допускается абсолютный путь профиля в `NEWEDITOR_USER_DATA`; обычный запуск использует системный профиль. Папка создаётся main. Доступ renderer к пути не предоставляется.

Версия схемы 1 — таблица `schema_migrations(version INTEGER PRIMARY KEY, name TEXT NOT NULL)`, первая строка `1 / bootstrap`. `PRAGMA user_version` и строка миграции меняются в одной транзакции. Перед миграцией проверяется отсутствие неизвестной новой версии. Настройки: WAL, foreign_keys, busy_timeout 5000 мс.

Развитие P4: к первоначальной v1 добавлена транзакционная миграция **v2 / local-persistence** по [спецификации хранения](spec-local-persistence.md). Текущий health возвращает 2 и проверяет также synchronous FULL; детали реализованного и оставшихся операций — в [отчёте P4](../trackers/track-local-persistence.md). Это не меняет границ исторического этапа P1.

`storage:health` выполняет фиксированную транзакцию во временной таблице: вставить значение, прочитать, удалить. Она не принимает SQL и не создаёт историю/черновики. Возвращает только `schemaVersion`. Проверки миграции дополнительно подтверждают повторное открытие, отказ новой схеме, commit и rollback.

Нативный `better-sqlite3` остаётся внешней зависимостью main, проходит `electron-builder install-app-deps` при установке и распаковывается из asar. Версия 13.2.0 поставляет N-API prebuilds: инструмент может использовать совместимый бинарник без компиляции C++. Проверка под обычным Node не заменяет проверку под Electron. UI-тест проверяет, что загруженный `.node` находится в зависимостях самого приложения, а не взят из внешнего `node_modules`.

## 4. Сборка и проверки

Команды: `dev`, `typecheck`, `lint`, `format:check`, `test`, `build`, `dist`, `dist:dir`, `test:native`, `test:electron`, `test:dev`. `check` объединяет быстрые проверки. Форматирование ограничено кодом/конфигурацией: оно не переписывает Markdown-fixtures.

С P4 нативный TypeScript-набор предварительно собирается Vite в `out/native-tests`. В electron-builder перечислены только runtime-каталоги `out/main`, `out/preload`, `out/renderer`: тестовые бандлы не должны попадать в поставку. Проверка содержимого asar дополняет запуск упакованного приложения.

Границы импортов проверяются отдельным небольшим скриптом на TypeScript AST: пути разрешаются компилятором; межмодульные обращения идут через index, граф соответствует архитектуре; чистые модули не импортируют платформенные зависимости. Скрипт проверяет также динамические импорты и require со строковым аргументом; вычисляемые импорты в src запрещены. Сам проверяющий код покрывается Vitest.

Playwright запускает настоящий Electron с изолированным профилем. Проверяет окно/React, ограниченный мост, отсутствие Node в renderer, параметры безопасности, отказ некорректным и frame-запросам IPC, запрет новых окон/навигации, вторичный запуск и SQLite через bridge. Тот же сценарий применяется к распакованному артефакту через `NEWEDITOR_EXECUTABLE`. Отдельный native-набор запускается бинарником Electron в режиме Node и проверяет сервис SQLite без UI. Это дополняет, но не заменяет проверку main/упакованного приложения.

`test:dev` собирает main/preload, поднимает renderer через `electron-vite dev --rendererOnly` и запускает те же сценарии с dev-URL. Сервер управляется Playwright и завершается после проверки; существующий процесс на порту 5173 не переиспользуется. Runtime-валидация неправильных DTO и subframe-флага покрыта unit-тестами, отказ чужому окну — дополнительно настоящим IPC в Electron.

Для Linux P1 проверяет распакованный каталог electron-builder. Пакеты поставки: Linux AppImage, Windows NSIS, macOS DMG для x64/arm64; выпуск и проверки остальных ОС относятся к P8. Сборка на Linux не означает проверки Windows/macOS. GUI-проверки требуют доступного DISPLAY или Xvfb; ограничение окружения фиксируется явно.

## 5. Запуск разработчиком

В корне репозитория, с Node.js из `.nvmrc`:

```sh
npm ci
npm run dev
```

`npm ci` вызывает подготовку нативных зависимостей Electron. Для сборки из исходников при отсутствии prebuild нужны Python и C++ toolchain. Не запускайте приложение с `--no-sandbox` ради обхода ошибок окружения: требуется исправная поддержка sandbox ОС.

```sh
npm run check
npm run test:native
npm run test:dev
npm run build
npm run test:electron
npm run dist:dir
```

`test:electron` проверяет ранее собранный `out`. Для проверки Linux-артефакта:

```sh
NEWEDITOR_EXECUTABLE="$PWD/dist/linux-unpacked/neweditor" npm run test:electron
```

В PowerShell переменные задаются через `$env:NEWEDITOR_EXECUTABLE = 'абсолютный путь к exe'`. Для профиля аналогично задаётся `NEWEDITOR_USER_DATA`. Обычный запуск без переменной использует стандартную папку Electron; тесты создают и удаляют только собственные временные профили. На headless Linux используйте `xvfb-run -a npm run test:electron`, если Xvfb установлен.

| Сборочная среда | Команда пакета | Артефакт | Проверка |
| --- | --- | --- | --- |
| Linux x64 | `npm run dist -- --linux --x64` | AppImage | Запуск пакета/каталога и SQLite |
| Windows x64 | `npm run dist -- --win --x64` | NSIS | Установка, запуск и SQLite |
| macOS arm64 | `npm run dist -- --mac --arm64` | DMG | Запуск и SQLite; подпись/нотаризация при поставке |
| macOS x64 | `npm run dist -- --mac --x64` | DMG | Запуск и SQLite; подпись/нотаризация при поставке |

Команды матрицы — инструкция, не свидетельство выполненной проверки. Фактические результаты находятся в трекере.

С P3 в каркасе доступен отдельный стенд Markdown в памяти. Его тесты входят в общие `test:electron`/`test:dev`. Production CSP разрешает inline-стили для CodeMirror, сохраняя запрет inline-скриптов; это не разрешение исполнять HTML документа.
