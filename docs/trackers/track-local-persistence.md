# Локальное хранение P4: прогресс и проверки

Начало: 2026-11-25.
Статус: **P4.1 завершён; P4.2 в работе, готов фундамент чтения/кодирования и схема БД**.
Основания: [спецификация хранения](../specifications/spec-local-persistence.md), [план](plan-desktop-v1.md).

## 1. Принятые решения P4.1

- Ресурс идентифицирует место хранения, DocumentId — рабочую линию документа. Save As сохраняет DocumentId, но не переносит историю старой цели. Прежнее содержимое подтверждённой существующей цели сохраняется до замены.
- История получает исходную версию существующего файла при первом открытии. Хранятся пять последних состояний, включая последнее; одинаковые соседние снимки не дублируются, A → B → A остаётся тремя состояниями.
- Кодировки определяются консервативно: строгий UTF-8, затем проверяемая Windows-1251; UTF-16/32 и NUL не поддерживаются. Подсказка реестра encoding/BOM применяется только при совпавших байтах. Нормализации текста/переводов строк нет.
- Сохранение связывает файловую замену с журналом SQLite; unknown отличается от not-written и history-pending. Восстановление не публикует temp поверх неизвестного внешнего состояния. Неопределённая старая запись блокирует дальнейшую автоматическую запись той же цели, но не Save As в другой ресурс.
- Реестр, история, журнал, черновики и границы очистки разделены; схема v2, миграции, состояния восстановления, права/алиасы и ограничения ОС описаны до кода.

Это проектные правила. Их наличие в спецификации не означает готового сохранения: большая часть сценариев P4 ещё не реализована.

## 2. Реализованный фундамент P4.2

- [Кодек](../../src/platform/desktop/main/persistence/codec.ts): iconv-lite 0.7.3, точные UTF-8/Windows-1251/BOM, round-trip, сохранность Unicode и переводов строк. Непредставимый текст не превращается в `?`. Неопределённый CP1251-байт `0x98` запрещён отдельно: iconv-lite отображает его в U+FFFD и обратно, из-за чего простой round-trip пропускал бы ошибку. Намеренный U+FFFD в UTF-8 разрешён.
- [Чтение файла](../../src/platform/desktop/main/persistence/file-reader.ts): один descriptor, stat до/после, проверка пути и длины, SHA-256 всех байтов и версионированная ревизия с inode/временами/правами. Обнаруженная гонка не возвращает частичный документ. Ссылки/каталоги не читаются как обычный файл; descriptor закрывается и при отказе.
- [SQLite](../../src/platform/desktop/main/database.ts): миграция v1 → v2 с пятью таблицами, FK, JSON/check-ограничениями и единственной активной операцией на ресурс. WAL + synchronous FULL + foreign_keys + busy_timeout проверяются health-транзакцией. Ошибка миграции не сбрасывает исходные данные, недостающая таблица не создаётся поверх объявленной готовой схемы.
- `storage:health` теперь возвращает схему **2**. Существующий ограниченный bridge не расширялся; renderer по-прежнему не имеет файловых полномочий.

## 3. Фактические проверки

Linux x64, Electron 45.4.1 / Node 24.22.3 / ABI 150; инструментальный Node 24.11.1. Другие ОС не проверялись.

- `TMPDIR=/tmp/opencode npm run check`: **144 unit-теста** в 8 файлах, типы domain/main/renderer, lint, границы и форматирование.
- Новые [24 теста кодека](../../tests/unit/local-codec.test.ts) и [14 тестов чтения](../../tests/unit/local-file-reader.test.ts) выполняются через Vitest в **инструментальном Node**, не выдаются за нативную проверку ФС под Electron. Проверены каждый определённый ненулевой CP1251-байт, U+FEFF/U+FFFD, суррогаты, BOM, NFC/NFD, смешанные окончания строк, одинаковая длина с прежним mtime, смена inode, подмена/удаление при чтении, неполный буфер, ошибки чтения/close и копирование подсказки до await.
- `TMPDIR=/tmp/opencode npm run test:native`: **10 проверок SQLite внутри Electron**, включая новую/старую/некорректную схему, откат частичной миграции, FK/ограничения, переоткрытие записей истории/журнала/черновиков/границ очистки. Это проверка схемы и долговечности строк, не реализация поведения портов истории/черновика.
- `npm run dist:dir`: сборка и распакованная Linux-поставка получены.
- По **2 GUI-регрессии каркаса** прошли в dev и packaged: IPC/sandbox/single-instance/нативная SQLite в собственном asar, схема 2 и отказ повреждённой БД без сброса. При первом прогоне тест ещё ожидал старую подпись «схема 1»; ожидание обновлено, оба набора повторно прошли.
- Markdown GUI-набор P3 в этом шаге повторно не запускался: редакторы и их интеграция не менялись. Его прежние результаты не обозначаются новым прогоном P4.
- Production `npm audit --omit=dev`: 0 уязвимостей. Полная установка по-прежнему сообщает 6 moderate-позиций инструментов сборки, ранее отмеченных в P1; небезопасный `audit fix --force` не применялся.
- Документация: 14 Markdown-файлов, 131 локальная ссылка, 45 уникальных задач (20 завершены); три извлечённых TypeScript-контракта компилируются. Markdown-fixtures не менялись, package.json/lockfile согласованы, `git diff --check` без ошибок.

Команды GUI-проверки после `dist:dir`:

```sh
TMPDIR=/tmp/opencode NEWEDITOR_TEST_DEV=1 npm run test:electron -- tests/electron/desktop.spec.mjs --output=/tmp/opencode/neweditor-p4-foundation-dev
TMPDIR=/tmp/opencode NEWEDITOR_EXECUTABLE="$PWD/dist/linux-unpacked/neweditor" npm run test:electron -- tests/electron/desktop.spec.mjs --output=/tmp/opencode/neweditor-p4-foundation-packaged
```

## 4. Что ещё не готово

- Реестр путей/разрешений, очередь ресурса и полноценный `DocumentStore` ещё не подключены. Низкоуровневый reader принимает **main-only канонический путь**, а не выданный renderer ref; он не является публичным IPC и сам не регистрирует историю.
- Схема таблиц существует, но репозитории/транзакции поведения истории и черновиков ещё не реализованы. Пользовательские файлы не сохраняются; прототип Markdown остаётся memory-only.
- Журнал prepared/replacing/file-written/settled/needs-attention пока только описан и имеет таблицу. Реальная запись, reconcile, принудительное прерывание процесса и восстановление — P4.3/P4.6.
- Наблюдение/polling, подавление событий своей записи и общий memory/local-контрактный набор ещё впереди. Проверка FIFO/подмен ФС непосредственно под Electron также остаётся для нативного набора P4.6.
- История/черновики/восстановление через UI — P5/P7; изображения/Markdown Save As — P6. Нельзя считать этот шаг завершением всего P4.

Следующий шаг: продолжить **P4.2** — реестр канонических ресурсов и main-only доступ к SQLite-репозиториям, согласованный load с исходной историей и очередь операций; затем P4.3 — восстанавливаемая запись.
