# Локальное хранение P4: прогресс и проверки

Начало: 2026-11-25.
Статус: **P4.1–P4.6 завершены на Linux x64; следующий этап — P5, файловый UI/IPC**.
Основания: [спецификация хранения](../specifications/spec-local-persistence.md), [план](plan-desktop-v1.md).

Разделы результатов ниже фиксируют состояние на завершение P4. Последующее подключение файлового UI/IPC, начиная с read-only открытия P5.1, описано в [отчёте P5](track-desktop-ui.md).

## 1. Принятые решения P4.1

- Ресурс идентифицирует место хранения, DocumentId — рабочую линию документа. Save As сохраняет DocumentId, но не переносит историю старой цели. Прежнее содержимое подтверждённой существующей цели сохраняется до замены.
- История получает исходную версию существующего файла при первом открытии. Хранятся пять последних состояний, включая последнее; одинаковые соседние снимки не дублируются, A → B → A остаётся тремя состояниями.
- Кодировки определяются консервативно: строгий UTF-8, затем проверяемая Windows-1251; UTF-16/32 и NUL не поддерживаются. Подсказка реестра encoding/BOM применяется только при совпавших байтах. Нормализации текста/переводов строк нет.
- Сохранение связывает файловую замену с журналом SQLite; unknown отличается от not-written и history-pending. Восстановление не публикует temp поверх неизвестного внешнего состояния. Неопределённая старая запись блокирует дальнейшую автоматическую запись той же цели, но не Save As в другой ресурс.
- Реестр, история, журнал, черновики и границы очистки разделены; схема v2, миграции, состояния восстановления, права/алиасы и ограничения ОС описаны до кода.

Это проектные правила. Их наличие в спецификации не означает готового сохранения: большая часть сценариев P4 ещё не реализована.

## 2. Реализованный фундамент P4.2

- [Кодек](../../src/platform/desktop/main/persistence/codec.ts): iconv-lite 0.7.3, точные UTF-8/Windows-1251/BOM, round-trip, сохранность Unicode и переводов строк. Непредставимый текст не превращается в `?`. Неопределённый CP1251-байт `0x98` запрещён отдельно: iconv-lite отображает его в U+FFFD и обратно, из-за чего простой round-trip пропускал бы ошибку. Намеренный U+FFFD в UTF-8 разрешён.
- [Чтение файла](../../src/platform/desktop/main/persistence/file-reader.ts): один descriptor, stat до/после, проверка пути и длины, SHA-256 всех байтов и версионированная ревизия с inode/временами/правами. Обнаруженная гонка не возвращает частичный документ. Ссылки/каталоги не читаются как обычный файл; descriptor закрывается и при отказе.
- [SQLite](../../src/platform/desktop/main/database.ts): миграция v1 → v2 с пятью таблицами, FK, JSON/check-ограничениями и единственной активной операцией на ресурс. WAL + synchronous FULL + foreign_keys + busy_timeout проверяются health-транзакцией. Ошибка миграции не сбрасывает исходные данные, недостающая таблица не создаётся поверх объявленной готовой схемы.
- `storage:health` теперь возвращает схему **2**. Существующий ограниченный bridge не расширялся; renderer по-прежнему не имеет файловых полномочий.
- [Реестр путей](../../src/platform/desktop/main/persistence/path-registry.ts): канонические существующие пути и отсутствующие save-target, повторная/параллельная регистрация, символьные алиасы и сохранение case-sensitive имён. Внешний rename не переносит старую историю по inode; разные hard-link пути доступны для чтения отдельно.
- [Репозиторий](../../src/platform/desktop/main/persistence/repository.ts): реестр и проверяемые JSON v1, исходная версия + счётчик + метаданные чтения в одной SQLite-транзакции; запросы истории с проверкой hash/Unicode/метаданных и безопасных чисел. Неизвестная версия/порча не маскируются пустой историей. ServiceDatabase выдаёт соединение только main-репозиториям.
- [Локальные сервисы](../../src/platform/desktop/main/persistence/local-services.ts): ref-разрешения на владельца, отзыв при отложенном чтении, стабильные DocumentId/resourceId после переоткрытия, полный DocumentStore и HistoryStore. Регистрация пути остаётся main-only; прежняя читающая фабрика сохранена как совместимый re-export.
- [Очередь ресурса](../../src/platform/desktop/main/persistence/queue.ts): разные владельцы разделяют последовательность одного ресурса, независимые ресурсы не блокируются; отказ задачи не отравляет следующий вызов. Фабрика переиспользуется для одного соединения. Подключение к жизненному циклу настоящего WebContents/IPC следует в P5.

### 3.3. Запись, журнал и политика истории P4.2–P4.4

- [Валидация](../../src/platform/desktop/main/persistence/save-data.ts) копирует plain DTO до первого await и вычисляет независимый от порядка полей fingerprint. Чужие ref/операции не дают доступ к файлу или результату записи. Ошибки формата/Unicode/кодировки не меняют файл.
- [Файловая запись](../../src/platform/desktop/main/persistence/file-writer.ts) создаёт соседний exclusive temp, синхронизирует descriptor, переносит POSIX mode/uid/gid, проверяет temp по dev/ino/hash и не удаляет чужие имена. Замена существующего файла не использует предварительный unlink; создание отсутствующего файла использует link без перезаписи.
- [Журнал](../../src/platform/desktop/main/persistence/save-journal.ts) и [координатор записи](../../src/platform/desktop/main/persistence/save-engine.ts) различают not-written/conflict/unknown/history-pending/saved. Полный клиент имеет save/getOperation/reconcile; ready выполняет стартовое восстановление. Закрытие владельца до prepared отменяет принятие; после prepared main завершает принятый запрос независимо от окна.
- Снимок версии, реестр и окончательный исход фиксируются одной транзакцией. История удерживает 5 последних состояний, включая последнее; полный no-op не пишет файл/версию, A → B → A сохраняет три состояния. ASCII encoding-only сохраняет те же байты, **но публикует новый inode/ревизию**: иначе другая сессия могла бы записать старые метаданные с прежней expectedRevision. Перед перезаписью добавляется недостающая внешняя редакция/содержимое неоткрытой цели Save As. Повтор старого operationId не пишет файл и после удаления его версии политикой пяти состояний.
- `TMPDIR=/tmp/opencode npm run check`: **163 unit-теста в 10 файлах**, типы/lint/границы/форматирование прошли; добавлены 15 тестов валидации/копирования/fingerprint.
- `TMPDIR=/tmp/opencode npm run test:native`: **99 проверок под Electron** — 10 схемы + 36 читающего подэтапа + 53 записи/журнала (включая вложенные случаи). Новый набор проверяет реальные ФС/SQLite; отказы операций/потеря ответа моделируются тестовыми обёртками FileWriteIO и SQLite-триггерами, а не production-переключателями.
- **Семь настоящих SIGKILL дочернего Electron-процесса:** prepared до фиксации identity; replacing до rename; после rename до receipt; file-written внутри транзакции истории; после settled; дополнительно encoding-only с одинаковыми байтами до/после публикации. Перезапуск различает эти состояния по ревизии, не повторяет запись/версию, не публикует temp автоматически и не перезаписывает последующее внешнее содержимое. В file-written-сценарии внешний файл меняется до восстановления — история подтверждённого снимка завершается отдельно от него.
- Проверены также: два клиента одной цели, pending во время записи, null/старая expectedRevision, исключение после rename/link, fsync/подготовка и очистка temp, SQLite-ошибки prepared/replacing/file-written/history, подмена/изменение temp, read-only/hard link, UTF-8 BOM/Windows-1251, новый пустой файл, Save As, обратный ход часов, повтор после перезапуска и порча pending-журнала. Отказ после начала публикации не объявляется not-written по одному исключению.
- Регрессия следующего save после reconcile выявила необходимость заново читать запись реестра: иначе новый preimage мог получить старую encoding и создать ложную before-overwrite-версию. Исправлено и проверено точным числом/содержимым трёх состояний истории. Повреждённый завершённый исход также не объявляется missing и не приводит к повторной записи того же ID.
- При сбое до сохранения tempIdentity остаётся **один недоказанный orphan**: тест подтверждает, что он не удаляется по имени. Новый снимок сохраняется в журнале, неизвестный внешний файл не перезаписывается. Автоматическая очистка таких orphan, UI разбора needs-attention и безопасная компактизация журнала требуют отдельной детализации P7; возможный рост служебных данных открыт явно.
- Production composition и файловый IPC/UI по-прежнему **не подключены**. Нативные SIGKILL-проверки фабрики не считаются проверкой восстановления пользовательской сессии через UI. Реальный ENOSPC носителя/обрыв питания, произвольные ACL/xattr, Windows/macOS и вся совокупность shared memory/local-контрактов остаются открытыми для P4.6/P8.

### 3.4. Черновики и наблюдение P4.5

- [Валидация черновика](../../src/platform/desktop/main/persistence/draft-data.ts) сохраняет полный рабочий Unicode, включая NUL и emoji при выбранной Windows-1251: кодек файла здесь не применяется. DTO копируется до await, нормализуется порядком полей и глубоко замораживается. [Репозиторий](../../src/platform/desktop/main/persistence/draft-repository.ts) хранит version-1 envelope, проверяет согласованность JSON с колонками и монотонность ревизии; clearance и условный DELETE выполняются одной immediate-транзакцией.
- Первый запрос нового ключа закрепляет его за владельцем; persisted ключ требует явного main-only recoverDraft. Чужие активные черновики не выдаются в списке восстановления. Восстановление ссылки location не выдаёт доступ к файлу. Закрытие освобождает права, но не удаляет record/clearance. Расписание и интерфейс восстановления остаются P7.
- [Наблюдатель](../../src/platform/desktop/main/persistence/resource-observer.ts) разделяет один watcher родительского каталога и polling между подписчиками ресурса, но хранит их ревизии раздельно. Сигналы объединяются за 100 мс, polling — 2000 мс; main-only refreshResources предназначен для будущего возврата фокуса. Общий байтовый probe не декодирует текст, поэтому замечает и неподдерживаемый файл. Ошибка watcher не отключает polling; callback-исключения изолированы, close/отписка освобождают ресурсы и отменяют ожидающую регистрацию.
- Свежая подтверждённая запись обновляет наблюдение только автора принятой операции, до освобождения очереди. Cached receipt и file-written reconcile не откатывают наблюдение к старому состоянию. Replacing с собственным новым hash ждёт reconcile; другое содержимое и удаление не подавляются. Чужой save между load и watch не теряется из-за обновления глобального реестра.
- При интеграции обнаружено затенение callback подтверждения локальной переменной: исправлено, все прежние 99 native-проверок восстановлены до расширения набора. Дополнительный unit-тест воспроизвёл потерю refresh между последней проверкой dirty и отдельным Promise.finally; освобождение running перенесено в тот же microtask. Проверены также синхронное закрытие из onError и отсутствие параллельных probe.
- Итоговый `npm run check`: **187 unit-тестов в 12 файлах**, типы/lint/границы/форматирование прошли. Добавлены 16 проверок DTO черновика и 8 проверок наблюдателя с детерминированными сигналами.
- Итоговый `TMPDIR=/tmp/opencode npm run test:native`: **119 проверок под Electron** — прежние 99 + 20 проверок P4.5 (включая вложенные). [Новый набор](../../tests/native/drafts-events.test.ts) проверяет реальные SQLite/ФС: монотонность и идемпотентность, rollback clearance при ошибке DELETE, сохранение после перезапуска, порчу JSON, права восстановления, новый черновик во время save, подавление только собственного события, cached/pending/file-written результаты, внешнее изменение/удаление/создание, fallback при ошибке watcher и закрытие сервиса после prepared. Семь SIGKILL предыдущего этапа прошли повторно.
- Настоящий fs.watch отдельно проверен внешней атомарной заменой и удалением файла. Остальные временные последовательности воспроизводятся инъекцией сигналов, без ожидания двухсекундных таймеров. Это Linux-проверка, не свидетельство работы watcher/прав на других ОС.
- `TMPDIR=/tmp/opencode npm run dist:dir` прошёл; по **2 GUI-регрессии каркаса dev/packaged** прошли (output: `/tmp/opencode/neweditor-p4-drafts-dev`, `/tmp/opencode/neweditor-p4-drafts-packaged`). ## 4. Что ещё не готово

- На завершение P4 публичного файлового IPC ещё не было. В P5.1 подключены только открытие/load и условная очистка при закрытии; файловая запись/история/наблюдение через UI остаются следующим подэтапам. Прототип Markdown остаётся memory-only.
- Репозиторий черновиков и наблюдатель/polling реализованы; расписание/восстановление сессий через UI — P7. Сам DocumentStore черновики не очищает и не обещает авточерновики отсутствующего UI.
- Общий memory/local-контракт, прикладная приёмка и приватные POSIX-права служебных файлов проверены. Новые файловые IPC/диалоги/подписки и graceful shutdown с ожиданием принятых операций нужно детализировать и подключить перед файловым UI в P5/P7; нынешний main пока использует только диагностическую БД.
- Windows/macOS, реальный ENOSPC/обрыв питания и произвольные ACL/xattr не проверены. Успех Linux/SIGKILL/инъекций ошибок не подменяет эти проверки; матрица платформ остаётся открытой.
- История/черновики/восстановление через UI — P5/P7; изображения/Markdown Save As — P6. Завершение P4 не означает готовую первую версию редактора.

Следующий шаг: **P5.1 — спецификация `spec-desktop-ui.md` перед реализацией вкладок/диалогов/безопасного файлового IPC**, затем создание и открытие документов через UI.
