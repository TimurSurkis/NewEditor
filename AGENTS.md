# Правила работы над проектом

Эти инструкции действуют для всего проекта. Подробные требования, архитектура и текущее состояние работы хранятся в `docs/`; этот файл фиксирует основные принципы для исполнителей.

## 1. Общение и самостоятельность

- Общайся с пользователем на русском языке, кратко и по существу.
- Пользователь делегировал исполнителю технические и типовые продуктовые решения в рамках согласованных требований. Принимай их самостоятельно, фиксируй решение и обоснование в документации.
- Уточняй с пользователем изменения явно заданных требований и вопросы, которые нельзя разрешить в рамках делегированных полномочий. Задавай вопросы по одному.
- Проект учебный: выбирай понятные решения и минимально необходимый набор технологий. Объясняй существенные архитектурные решения простыми словами.

Перед работой определи текущий этап по трекеру и прочитай относящиеся к задаче спецификации. Отличай принятые решения от черновиков, гипотез и непроверенных предположений.

Проектные документы размещай в `docs/`:

| Каталог | Префиксы |
| --- | --- |
| `docs/concepts/` | `concept-` — концепции; `idea-` — идеи |

Имена файлов — `kebab-case`, текст — на русском языке. Корневой `AGENTS.md` служит инструкцией исполнителям. Новые документы добавляй в навигацию, где это необходимо; ссылки поддерживай актуальными.

## 3. Document-first

Применяем подход в двух смыслах:

1. Сначала фиксируем требования, контракты, поведение и критерии проверки в документации, затем реализуем соответствующую задачу.
2. Архитектура строится вокруг модели документа.

Детализируй спецификации по этапам плана. Перед кодом доводи спецификацию текущей задачи до достаточной точности. Если реализация или прототип требуют изменения решения, сначала зафиксируй причину и обнови затронутые документы.

Концепция определяет требования, архитектурная спецификация — границы реализации, профильные спецификации — детали поведения, трекер — порядок и фактический прогресс. Поддерживай их согласованность.

## 4. Границы продукта и стек

- Первая версия — Electron для Windows, macOS и Linux: локальные TXT и Markdown, вкладки, исходный и визуальный режимы Markdown, форматирование, поиск и замена.
- Вторая версия — личные облачные библиотеки, доступные в браузере и Electron. Для облачных документов требуется подключение к серверу.
- Базовый код, DOCX и другие форматы импорта относятся к последующему развитию согласно концепции.
- Основа реализации: TypeScript со строгой проверкой типов, React, Node.js и SQLite. Будущий сервер — Express.
- Для сборки используются electron-vite/Vite и electron-builder, для SQLite — `better-sqlite3`. Остальные выбранные инструменты и версии смотри в архитектурной спецификации.
- При первичной настройке используй актуальный стабильный Electron. Фиксируй совместимые версии зависимостей и lockfile; обновления проверяй. Нативную SQLite проверяй под ABI Electron, включая упакованную сборку.

## 5. Модульная архитектура

- Сохраняй простую модульную структуру с явными контрактами и возможностью расширять форматы, хранилища и клиенты.
- Соблюдай разделение `core`, `ports`, `formats`, `application`, `ui`, `platform` и будущего `server` по архитектурной спецификации.
- `core`, `ports`, `application` и чистая логика форматов независимы от React, Electron, Node `fs`, SQLite и Express.
- UI вызывает сценарии приложения. Конкретные операции хранения выполняют адаптеры портов; зависимости подключаются в точках запуска.
- SQL, файловые операции и миграции находятся в платформенных или серверных реализациях. Замена хранилища должна сохранять прикладные контракты.
- Рабочая сессия находится в renderer; файлы, SQLite и локальное сохранение — в main. Между ними используется ограниченный preload/IPC-интерфейс.
- Возможность подключить новое хранилище и перенос существующих данных — отдельные задачи. Перенос текста, вложений и истории требует явно описанного сценария.

## 6. Модель документа и Markdown

- Основное содержимое TXT/Markdown — исходный текст. Визуальное дерево и состояние библиотеки редактора являются производными представлениями.
- Оба режима используют одну сессию документа, общую последовательность текстовых правок и согласованную отмену/повтор действий.
- Нетронутые участки Markdown сохраняют исходное написание. Нормализация допустима внутри изменённого фрагмента; форматирование всего документа выполняется отдельной командой пользователя.
- Неподдерживаемую разметку сохраняй. Переключение режима само по себе не меняет содержимое и не создаёт сохранённую версию.
- Проверяй ревизию при применении правок и результатов фоновых операций: устаревший результат не должен заменять новое состояние.
- CodeMirror и ProseMirror проходят ранний прототип на сохранение исходника и общую отмену действий. Проверяй выполнение требований примерами и тестами, прежде чем развивать полноценный визуальный режим.

## 7. Сохранность данных

- Исходный файл меняется при явном сохранении. Авточерновик — отдельный механизм восстановления.
- Храни пять последних сохранённых состояний, включая последнее сохранённое. Авточерновики не расходуют этот лимит; сохранение без изменений не создаёт дубликат версии.
- Локальная история и черновики находятся в служебной SQLite приложения. TXT/Markdown остаются обычными файлами; вставленные изображения размещаются рядом в папке `<имя документа>.assets` с относительными ссылками.
- Новые файлы создаются в UTF-8 без BOM. Существующие файлы сохраняют кодировку и текстовое представление согласно профильной спецификации; поддерживаются UTF-8 и Windows-1251.
- При внешнем изменении чистый документ перечитывается. При собственных несохранённых правках сохраняй рабочий текст и предоставляй сравнение, без автоматической перезаписи конфликта.
- Сохранение работает с конкретным снимком. Подтверждение старого снимка не должно терять более новые правки или черновики.
- Локальная запись файла и истории связана восстанавливаемым журналом. Различай ошибку записи содержимого и частично завершённую фиксацию истории.
- Для облака права, версии и исключительный доступ контролирует сервер. Документ удерживает одна клиентская сессия через серверную аренду; запись требует актуальных прав, аренды и ревизии.

## 8. Прогресс и проверка результата

- Выполняй задачи по зависимостям плана; поддерживай текущую задачу и следующий шаг в трекере.
- Отмечай задачу завершённой только после получения результата и необходимых проверок. Записывай результат, выполненные проверки и фактические ограничения в журнале.
- После каждого завершённого пункта плана делай отдельный коммит с относящимися к нему кодом, тестами и документацией. Не включай посторонние изменения. Push выполняй только по отдельной просьбе пользователя.
- Проверяй значимые свойства: преобразование Markdown, сохранность данных, частичные сбои, контракты модулей и пользовательские сценарии.
- Используй проверки типов, тесты и сборку соразмерно изменению. Конкретные команды бери из существующей конфигурации проекта; не представляй запланированный инструмент как уже настроенный.
- Для документации проверяй согласованность решений, ссылки и актуальность статусов.
- Результаты одной ОС не считаются проверкой остальных. Невыполненные проверки явно оставляй открытыми в матрице платформ.
- Актуальные версии пакетов, номера текущих задач и подробные параметры поведения поддерживай в профильных документах и трекере; при изменении основных принципов обновляй также этот файл.
