# Архитектура текстового редактора

Версия архитектуры: **1**.
Статус: **зафиксированная архитектурная основа для реализации и детализации**.
Основание: [концепция проекта](../concepts/concept-project.md).

Документ фиксирует проектные решения на основе согласованных требований. Он является основным источником сведений о модулях, зависимостях и размещении компонентов. Согласованные пользователем требования находятся в концепции; выбор библиотек редакторов и детали пользовательских сценариев уточняются в отдельных спецификациях.

## 1. Архитектурное решение

Используем **модульное приложение с общим документным ядром и адаптерами платформы и хранения**.

- Первая версия: Electron, React, Node.js, локальные TXT/Markdown и служебная SQLite.
- Вторая версия: тот же интерфейс и общая логика документов в браузере и Electron; облачный сервер — модульный монолит на Express и SQLite.
- Основное содержимое текстового документа — исходный текст. Форматирование, вкладки и место хранения имеют отдельную ответственность.
- Модульность обеспечивается обычными каталогами исходников, явными зависимостями и небольшими контрактами.
- Начальная единица развёртывания облака — один сервер приложения с одной SQLite. Расширение инфраструктуры выполняется по мере появления нагрузки.

**Порт** — интерфейс операции, необходимой приложению, например загрузки документа. **Адаптер** — конкретная реализация этого интерфейса, например обращение через Electron IPC или HTTP.

## 2. Компоненты и размещение

### 2.1. Десктоп, первая версия

```text
Electron renderer
┌───────────────────────────────────────────────────┐
│ React UI + интеграции редакторов                   │
│                      ↓                            │
│ Application: сессии и сценарии документов          │
│          ├── Core: модель, правки, отмена           │
│          ├── Formats: TXT, Markdown                │
│          └── Ports → клиентский IPC-адаптер        │
└──────────────────────┬────────────────────────────┘
                       │ ограниченный preload API
                       ▼
Electron main
┌───────────────────────────────────────────────────┐
│ Файловые диалоги и обработчики IPC                 │
│ Локальный сервис сохранения и восстановления      │
│          ├── файловая система: TXT, MD, assets     │
│          └── SQLite: история, черновики, связи     │
└───────────────────────────────────────────────────┘
```

Рабочий текст и состояние редактирования принадлежат renderer. Файлы, SQLite, наблюдение за файлами и фиксация сохранений принадлежат main. Main последовательно выполняет сохранения одного документа, в том числе при запросах из разных окон.

Для одного профиля приложения работает один main-процесс. Повторный запуск передаёт ему запрос на открытие файлов; это сохраняет единого владельца локальной очереди записи и служебной базы.

Preload предоставляет именованные операции и сериализуемые данные. Renderer получает доступ к выбранным документам через выданные main идентификаторы ресурсов. В Electron включены изоляция контекста и sandbox; Node.js доступен платформенной части, а прямой Node integration в renderer выключен.

### 2.2. Облако, вторая версия

```text
Electron / браузер
  React UI → Application → Core + Formats
                  │
             HTTP-адаптер
                  │ HTTPS
                  ▼
  Express API → серверные сценарии
                  ├── пользователи и библиотеки
                  ├── доступ и блокировки
                  ├── сохранение, версии, черновики
                  └── репозитории SQLite
```

Electron выбирает адаптер по месту хранения документа. Браузер работает с облачной библиотекой. Каждый клиент содержит собственную рабочую сессию; сервер является авторитетной стороной для сохранённого содержимого, доступа, версий и блокировок.

## 3. Модули и правила зависимостей

| Модуль | Ответственность | Допустимые зависимости внутри проекта |
| --- | --- | --- |
| `core` | Документ, снимки, текстовые правки, ревизии, отмена/повтор, сравнение состояний | Самодостаточная логика и структуры данных |
| `ports` | Контракты хранения, истории, черновиков, вложений и доступа; результаты и ошибки операций | `core` |
| `formats` | TXT/Markdown, разбор с исходными диапазонами, преобразование форматирования в правки | `core` |
| `application` | Сессии документов, открытие, сохранение, восстановление, координация режимов | `core`, `ports`, `formats` |
| `ui` | React-компоненты, вкладки, команды, поиск/замена, интеграция движков редакторов | Публичные интерфейсы `application`, структуры `core` и `formats` |
| `platform` | Точки запуска, Electron bridge, HTTP-адаптер, файловые диалоги, локальные реализации портов | `ports`, `core`; подключение `application`, `formats` и `ui` в точках запуска |
| `server` | Express-маршруты, серверные сценарии доступа и сохранения, SQLite-репозитории | Общие структуры `core`/`ports`; собственные серверные модули |

Правила:

1. `core`, `ports`, `application` и чистая часть `formats` не импортируют React, Electron, Node `fs`, SQLite или Express.
2. UI вызывает сценарии приложения; SQL и файловые операции выполняют адаптеры.
3. Адаптеры реализуют порты. Общие сценарии получают нужные реализации при запуске через параметры.
4. Форматы регистрируются явно в точке запуска. Реестр связывает идентификатор формата с его обработчиком.
5. Модули обращаются к публичным точкам входа друг друга. Циклические зависимости устраняются переносом общей структуры в `core` или контракта в `ports`.
6. Модель и сценарии доступны для проверки без запуска Electron и React.

Сторонние редакторы подключаются через небольшие интеграционные модули UI. Их внутреннее состояние не передаётся в хранилище и не становится форматом документа.

## 4. Документ, сессия и представления

Модель `Document` содержит:

- `id` — внутренний идентификатор;
- `format` — формат документа;
- `text` — текущий исходный текст;
- `location` — ссылка на ресурс хранилища, отсутствующая до первого сохранения нового документа;
- `fileMetadata` — кодировка и сведения о текстовом представлении;
- `sourceRevision` — возрастающая ревизия рабочего текста.

`DocumentSession` содержит документ, последнее подтверждённое сохранённое состояние, ревизию хранилища, состояние операций и конфликта, стек отмены/повтора. `sourceRevision` учитывает изменения текста, а `stateRevision` в состоянии сессии — изменения текста или сохраняемых метаданных. Это сохраняет корректный порядок авточерновиков и при смене кодировки без изменения текста. Признак несохранённых изменений определяется сравнением сохраняемых данных, а не только номеров ревизий.

`TabState` содержит выбранный режим, курсор, выделение и прокрутку. Сценарии приложения владеют сессиями; React подписывается на их изменения и отправляет команды.

У нового документа сразу есть идентификатор для авточерновика. Хранилище связывает постоянный ресурс с идентификатором документа. Идентичность ресурса определяется внутри адаптера: локальным реестром файлов или серверным ID. Ключ связи включает идентификатор хранилища, поэтому одинаковые пути в разных хранилищах не смешивают истории.

Детальная семантика полей и операций развивается в [спецификации модели документа](spec-document-model.md).

### 4.1. Исходный и визуальный режимы

Оба режима используют одну последовательность изменений исходного текста:

```text
Действие пользователя
       ↓
Интеграция редактора / обработчик формата
       ↓ текстовые замены для известной sourceRevision
Application → Core: проверка и применение правок
       ↓
Обновлённый текст → обновление активного представления
```

Для Markdown структура разбора является производным представлением с привязкой к исходным диапазонам. Визуальная операция формирует замену затронутого синтаксического фрагмента. Переключение режимов само по себе не переписывает текст.

Неподдерживаемая разметка сохраняется как исходный фрагмент, доступный через исходный режим. Результаты разбора и операции, построенные для старой ревизии, проверяются перед применением.

Стек отмены принадлежит сессии документа. Интеграции редакторов передают команды отмены и повтора в общую сессию. Это требование проверяется вместе с сохранением исходного Markdown при выборе движков.

## 5. Контракты хранения

Смысл операций описан ниже; точные методы, DTO результатов и локальные IPC-сообщения зафиксированы в [контрактах модулей](spec-module-contracts.md).

| Порт | Основные операции | Где выполняется реализация |
| --- | --- | --- |
| `DocumentStore` | Загрузить снимок; сохранить снимок с ожидаемой ревизией и ID операции | Локальный сервис в main или облачный сервер |
| `HistoryStore` | Получить список версий и содержимое выбранного снимка | SQLite соответствующего хранилища |
| `DraftStore` | Записать, получить и удалить черновик с ревизией исходного состояния | Локальная SQLite; во второй версии также серверная SQLite |
| `AssetStore` | Добавить вложение и разрешить ссылку на него | Файлы рядом с локальным документом или облачное хранилище вложений |
| `AccessLease` | Получить, продлить и освободить исключительный доступ | Облачный сервер |
| `ResourceEvents` | Подписаться на изменение или удаление ресурса | Локальное наблюдение за файлами; другие реализации по возможностям хранилища |

`AccessLease` и `ResourceEvents` подключаются по возможностям хранилища. Общий сценарий явно учитывает наличие этих возможностей.

Ключевые данные на границе:

- `StorageRef`: идентификатор хранилища и непрозрачная ссылка на ресурс.
- `DocumentSnapshot`: текст и сохраняемые метаданные.
- `StorageRevision`: значение, выданное адаптером для проверки внешних изменений.
- `operationId`: идентификатор конкретного запроса сохранения для повторов и восстановления после сбоя.
- `accessHandle`: сведения о текущем исключительном доступе для облачных операций.

Сохранение содержимого и создание версии координируются внутри реализации `DocumentStore`. Клиент не создаёт отдельную версию вторым независимым запросом. Политика удерживает пять последних сохранённых состояний, включая последнее сохранённое: до четырёх более ранних версий. Несохранённое рабочее состояние и авточерновик в этот лимит не входят. Политика находится рядом с сервисом сохранения.

Исторический снимок восстанавливается в рабочую сессию через обычный механизм изменений. Его последующее явное сохранение проходит тот же путь, что и другие правки.

### 5.1. Результаты операций

Транспорт передаёт структурированные результаты: успешная запись, конфликт ревизии, отказ доступа, занятый документ, ошибка чтения/записи и частично завершённая запись.

Состояние «файл записан, фиксация истории ожидает восстановления» отличается от «файл не записан». При потере ответа на облачный запрос клиент выясняет результат по `operationId`; повтор не должен создавать вторую версию.

## 6. Хранение данных

### 6.1. Десктоп

- Содержимое TXT/Markdown хранится в выбранном пользователем файле.
- Изображения сохраняются в `<имя документа>.assets` с относительными ссылками.
- В служебной папке приложения находится одна SQLite с реестром локальных документов, снимками версий, авточерновиками и незавершёнными операциями сохранения.
- Записи версии содержат снимок текста и метаданные его сохранения. Черновики имеют отдельные записи и отдельные правила очистки.
- Добавляемые изображения получают уникальные имена. Удаление ссылки меняет текст; физическое удаление вложения имеет отдельный жизненный цикл.

### 6.2. Облако

Начальная серверная SQLite содержит пользователей, библиотеки, документы, предоставленный доступ, версии, блокировки, результаты операций и черновики. Для обычных вложений первой облачной реализации используется отдельная таблица бинарных данных, доступная через `AssetStore`.

Серверные черновики привязаны к пользователю, клиентской сессии и документу. Они не являются сохранённой версией документа. Проверка доступа применяется также к истории, черновикам и вложениям.

Схема SQLite изменяется версионируемыми миграциями. SQL сосредоточен в репозиториях платформы и сервера. Браузер взаимодействует с ними через API.

## 7. Сохранение и восстановление после сбоя

### 7.1. Общий сценарий

1. Application фиксирует снимок рабочего состояния и создаёт `operationId`.
2. Адаптер получает снимок, ожидаемую ревизию хранилища и сведения о доступе.
3. Реализация проверяет возможность записи и выполняет сохранение с учётом истории.
4. Подтверждение записи обновляет базу сравнения именно записанным снимком. Более поздние правки остаются в редакторе.
5. Авточерновики очищаются только в пределах подтверждённого состояния; более новый черновик сохраняется.

Для одного документа записи выполняются последовательно. Авточерновик планируется через одну секунду после последней правки, а при непрерывном вводе — каждые пять секунд; он не меняет исходный файл. Старый запрос записи черновика не заменяет более новую ревизию той же сессии.

### 7.2. Локальная фиксация

Файл и SQLite не образуют общую транзакцию. Для связи двух записей используется небольшой журнал незавершённых сохранений в SQLite:

1. Проверить известное состояние файла и возможность кодирования текста.
2. Записать намерение сохранения: `operationId`, ресурс, ожидаемое состояние и новый снимок.
3. Подготовить временный файл рядом с целевым и заменить целевой файл с использованием возможностей атомарной замены на платформе.
4. В транзакции SQLite зафиксировать версию, обновить сведения о файле, применить политику удержания версий и завершить операцию журнала.

Перед заменой повторно проверяется состояние файла. Внешняя программа не обязана соблюдать блокировки редактора: локальная проверка ревизии обнаруживает изменения, но не является атомарным compare-and-write с произвольным сторонним процессом. Облачная проверка выполняется транзакционно.

Если завершение SQLite не удалось после записи файла, операция остаётся восстанавливаемой. При запуске приложение сопоставляет незавершённую запись с фактическим файлом: совпавший новый снимок позволяет завершить историю; несовпадение сохраняет снимок как материал восстановления и требует разрешения конфликта. Восстановление не перезаписывает неизвестное внешнее состояние автоматически.

До следующего сохранения того же документа сервис завершает незавершённую фиксацию или возвращает её ошибку. Новая запись не обгоняет незавершённую операцию истории.

Детали файловой замены, прав доступа и сброса данных на диск проверяются на Windows, macOS и Linux.

### 7.3. Облачная фиксация

Сервер в одной транзакции SQLite проверяет права, действующую блокировку и ожидаемую ревизию, обновляет документ, создаёт версию и сохраняет результат операции. Уникальный `operationId` делает повтор завершённого запроса идемпотентным.

Проверка авторизации выполняется и при повторном запросе. Транспортная ошибка не трактуется автоматически как отсутствие записи на сервере.

## 8. Облачный доступ и блокировки

У пользователя собственная библиотека. Владелец предоставляет доступ к документу зарегистрированным пользователям; получатель может читать и редактировать документ.

Исключительный доступ реализуется **серверной арендой блокировки**:

- В SQLite хранится одна действующая блокировка документа: держатель-сессия, токен поколения и время истечения.
- Получение блокировки атомарно. Содержимое документа загружается после её получения.
- Клиент периодически продлевает аренду и освобождает её при закрытии.
- При истечении аренды следующая выдача получает новый токен поколения. Запросы старого держателя больше не принимаются.
- Сервер проверяет доступ и актуальную аренду при чтении содержимого, истории и вложений, а также при сохранении. Обход блокировки через другой endpoint не допускается.

Блокировка относится к клиентской сессии: второе окно или устройство также получает отказ при занятом документе. При потере подтверждённой связи или права доступа клиент приостанавливает редактирование и сохраняет имеющиеся правки в своей рабочей сессии. Для продолжения требуется снова получить доступ и проверить серверную ревизию. Автоматического применения правок поверх чужой новой версии нет.

Время аренды и частота продления — параметры конфигурации будущей облачной версии. Уже доставленные серверу авточерновики доступны для восстановления после получения необходимых прав; несохранённый текст в памяти сам по себе не является гарантией восстановления после закрытия клиента.

## 9. Структура исходников

Один репозиторий, общая конфигурация проекта и обычные каталоги модулей:

```text
docs/
src/
  core/                 # документ, снимки, правки, undo/redo
  ports/                # интерфейсы внешних операций и результаты
  formats/
    txt/
    markdown/
  application/          # сессии и сценарии работы с документами
  ui/
    components/
    editors/            # интеграции исходного и визуального редакторов
  platform/
    desktop/
      main/             # файлы, SQLite, IPC, локальное сохранение
      preload/          # ограниченный мост
      renderer/         # подключение UI, сценариев и адаптеров
    web/                # точка запуска браузера, вторая версия
    cloud/              # общий HTTP-адаптер двух клиентов, вторая версия
  server/               # вторая версия
    http/               # маршруты и транспортная проверка входных данных
    services/           # библиотеки, доступ, блокировки, сохранение
    repositories/       # SQLite и миграции
```

Это структура будущей реализации. Каталоги второго этапа появляются вместе с соответствующими функциями. Точки запуска собирают зависимости; сборка браузера использует только браузерные и общие модули.

## 10. Расширение и масштабирование

| Изменение | Место расширения |
| --- | --- |
| Дополнительный текстовый формат | Обработчик в `formats` и регистрация его возможностей |
| DOCX и другой импорт | Импортёр с результатом в поддерживаемой модели; самостоятельный просмотр может иметь собственное представление |
| Другое хранилище | Реализация портов и подключение в точке запуска |
| Новый редактор исходника или визуального режима | Интеграция в `ui/editors`, сохраняющая общий протокол правок |
| Изменение базы данных | Репозитории и миграция данных при сохранении прикладных контрактов |
| Рост размеров вложений | Другая реализация `AssetStore` |
| Несколько экземпляров сервера | Общее согласованное хранилище документов, операций и блокировок |

Модульность позволяет менять конкретные реализации. Горизонтальное масштабирование сервера потребует отдельной инфраструктурной работы и общего хранилища с нужными гарантиями транзакций; первый этап использует SQLite и один сервер.

## 11. Проверка архитектуры

До полноценной реализации визуального режима выполняется документированный прототип выбранной связки CodeMirror 6 и ProseMirror по [спецификации Markdown](spec-markdown-editing.md) и её проверочным примерам. Он проверяет сохранение нетронутого Markdown, переключение режимов, неподдерживаемые фрагменты и общую отмену действий. Результат фиксируется в P3 плана. Если связка не выполняет требования, исполнитель документирует причину и меняет техническую реализацию, сохраняя требования и контракты.

Проверки архитектурных границ при реализации:

- Ядро и сценарии запускаются с тестовыми реализациями портов без Electron/React.
- Один контракт сохранения проверяется на локальном и будущем облачном адаптере.
- Ошибка или обрыв на каждом этапе сохранения оставляет распознаваемое состояние для восстановления.
- Редактирование во время сохранения не теряет более новые правки.
- Внешнее изменение локального файла не затирает рабочую сессию с собственными правками.
- В облаке два клиента не получают действующую аренду одновременно, а запрос старого держателя отклоняется.

## 12. Зафиксированные решения и дальнейшая детализация

Архитектурная основа включает: общее документное ядро; текст как основное содержимое; одну последовательность правок; отдельные сценарии и UI; порты хранения; Electron main как владельца локальных ресурсов; Express как владельца облачных правил; SQLite; восстанавливаемую локальную запись; серверные аренды блокировок.

Детализация по следующим документам:

1. [Модель документа](spec-document-model.md) — контракт P0.1 зафиксирован для реализации ядра.
2. [Контракты модулей и транспортов](spec-module-contracts.md) — методы, сообщения и категории ошибок зафиксированы в P0.2.
3. [Markdown](spec-markdown-editing.md) — контракт интеграции и программа прототипа зафиксированы в P0.3–P0.4; фактическая проверка движков выполняется в P3.
4. Локальное сохранение и восстановление — схема SQLite, файловые операции, история и авточерновики.
5. Облачные функции — API, пользователи, доступ, аренды и серверные транзакции ко второму этапу.

Инструменты выбраны в разделе 1.1; этапы, зависимости, задачи и критерии результата находятся в [плане-трекере десктопной версии](../trackers/plan-desktop-v1.md). Детализация контрактов, кодировок, «Сохранить как» и схем SQLite выполняется перед реализацией соответствующего этапа. Исполнитель принимает и фиксирует оставшиеся технические решения в рамках делегированных полномочий.
