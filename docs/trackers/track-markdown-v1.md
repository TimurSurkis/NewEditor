## 1. Результат P6.1

- Уточнён продуктовый профиль CommonMark/GFM: чтение и обычные/структурные действия с абзацами, heading, inline/code, цитатами, списками/задачами, таблицами, code-block, links/images и thematic breaks. Сноски/диаграммы/формулы не включены. Точное множество возможностей задано спецификацией, а не списком возможностей стороннего парсера.
- Зафиксированы правила inline-выделения/пустой каретки, split/join/Enter/Tab, минимальная область нормализации, reference-ссылки и image-диалог. Для каждого структурного действия требуется атомарная исходная транзакция и общий undo, не сериализация всего PM-document. Однозначный source fallback остаётся для неподдерживаемых/неоднозначных фрагментов, но не заменяет обычные обязательные функции GFM.
- Search в visual использует прежнюю буквальную source-семантику с явной подписью. Скрытый match/замена переводят в source через flush. Mode/кеш/выделение принадлежат существующей SessionId; сохранение/закрытие/внешний конфликт используют тот же P5-путь. Асинхронные parse/preview и диалог проверяют ревизии/owner/поколение.
- HTML никогда не исполняется, external images не загружаются. Внешние ссылки http/https открываются только явной командой с подтверждением и повторной проверкой в main; другие схемы не передаются ОС. Локальная документная ссылка требует фактического выбора в системном диалоге. Relative raster preview ограничен поддеревом owner, проверками пути/байтов/MIME/размеров и будущим AssetStore P6.3. CSP не ослабляется до кода этого шага.
- [16 новых нормативных fixtures](../specifications/fixtures/spec-markdown-v1-cases.json) фиксируют 14 успешных source-преобразований и 2 отказа: Setext→ATX, backtick-run inline-code, remove-link/изменение одного reference-употребления, split paragraph/task, пустой nested-list/outdent, list conversion/indent, удлинение code fence, escaped pipe/table structure/alignment, quote, пересечение HTML и multiline paste в ячейку. На момент P6.1 команды не выполнялись тестовым драйвером (`specified-not-executed`); результат частичного исполнения P6.2 указан в разделе 6. Прежние MD-01–MD-12 не изменялись.
- Для задержки P3 задан порядок P6.2: не привнести полный parse в source-path, кешировать по сессии/ревизии, локально обновлять visual при доказуемой области, измерить; при необходимости вынести полный parse в worker с ревизионным протоколом. Зафиксированы будущие бюджеты и изолированный packaged-benchmark с median/p95, а не обещание, что оптимизация уже выполнена.
- Никакие runtime-код, preload/CSP, зависимости, миграции и старые fixtures на этом пункте не менялись. P6.1 — document-first подготовка, не перенос прототипа в файлы.

## 3. Проверка решений и fixtures

Проверен **реальный установленный** unified/remark-парсер на отдельных входах, без изменения source:

- `~one~` и `~~two~~` дают delete-узлы: профиль читает оба вида, новая strike-команда создаёт `~~`.
- Сноска даёт footnoteReference/footnoteDefinition — значит, исключение из продукта должно проверяться явно в проекции/planner, а не предполагаться по отсутствию парсера.
- GFM literals дают link URL `http://www…`, `https://…` и `mailto:…`; распознавание URL не равно разрешению его открыть.
- Indented и fenced code дают code-узлы, но текущий projection консервативно защищает indented. HTML даёт html-узел либо смешанные children; table хранит left/right alignment, пока не используемый полностью visual.
- Пустой `- [ ] ` не даёт checked=false: парсер оставляет `[ ]` текстом. Это отдельно описано как незавершённый task-префикс для Enter/outdent; MV-07 использует обычный пустой listItem, чтобы не выдавать незавершённый task за распознанную задачу.

Структурная проверка новых fixtures проверяет JSON-версию/status, 16 уникальных ID, выбор ровно одного select/caretAfter, единственность выбранного фрагмента/области, допустимый Unicode/CRLF-диапазон, точный префикс/суффикс и неизменность rejected. Дополнительно source/expected разбираются установленным парсером, проверяются ожидаемые структурные узлы. Это **не** выполнение будущих formatting/PM-команд и не прохождение MG-01–MG-10. Интеграционные драйверы добавляются в P6.2; при несовпадении нужно исправлять реализацию, а не переписывать expected без пересмотра решения.

Проверки P6.1 соразмерны документации: ссылки/статусы/кодовые блоки и извлечённые TypeScript-контракты, неизменность runtime/старых fixtures/lockfile; `npm run check` — регрессия существующей основы. Последние native/GUI/packaging результаты — P5.5 (165 native, по 57 GUI); они не обозначаются повторными P6-проверками.

Фактический итог: структурная проверка всех 16 fixtures и ожидаемых AST прошла; MD-01–MD-12 остались неизменными. `npm run check` прошёл: 250 unit-тестов в 19 файлах, domain/main/renderer-типы, lint/границы/форматирование. Проверены 18 Markdown-файлов, 229 локальных ссылок, 45 уникальных задач (31 завершена) и компиляция трёх извлечённых TypeScript-контрактов. Runtime/tests/CSP/зависимости/lockfile не менялись; `git diff --check` без ошибок.

## 5. Первый инкремент P6.2: контракт до кода

P6.2 выполняется по внутренним инкрементам, без объявления пункта завершённым раньше всей матрицы. Первый инкремент подключает source/visual к существующему WorkspaceEditor: mode/ленивый parse-кеш на SessionId, общий flush/undo/save, исходные выделения и source-поиск из visual. TXT остаётся прежним и не получает parse. Базовая панель предоставляет heading/paragraph, strong/emphasis/strike и inline-code; новые чистые planners проверяют диапазоны/opaque/границы entities и не заменяют всю строку на предполагаемый expected.

Смена режима сначала flush и проверка поколения активации, затем подготовка кадра, затем уничтожение старого движка. Ошибка/pending оставляет старый движок живым. RequestSource от защищённого узла меняет mode, а не только выделение. В поиске видимый однозначный match остаётся visual, скрытый match и любая replace-команда переходят в source до исходной транзакции. Разбор не выполняется от source-ввода/selection/metadata, только по запросу visual/format; холодный синхронный parse и полный повторный visual parse пока остаются известным ограничением, **не результатом оптимизации MG-10**.

Проверки первого инкремента: unit mode/ABA/IME/pending/кеш/форматирование и GUI файловых MD с переключением/undo/save/reopen, двумя вкладками, поиском, конфликтом и безопасным opaque/remote-placeholder. Требования структурных list/table/code-действий, полноценные dialogs/link-IPC и изолированный benchmark не снимаются и остаются внутри P6.2. До их реализации UI явно обозначает промежуточный статус visual-интеграции.

При проверке границ первого инкремента отдельно проверяются пустые ATX-заголовки и столкновения добавляемых inline-маркеров с исходными: неоднозначный диапазон отвергается до транзакции. Инертная DOM-метка ссылки содержит только числовую исходную позицию, не URL; обратный DOM-разбор восстанавливает тот же mark при IME. Это не активация ссылки и не новый файловый/сетевой IPC.

## 7. Второй инкремент P6.2: контракт структурного ввода до кода

Первый структурный subset — верхнеуровневые непустые paragraph/heading: Enter разделяет блок, Shift+Enter создаёт hard break в paragraph, Backspace/Delete на границе соединяют соседние paragraph без добавочного символа. Heading при split сохраняется слева (ATX), справа создаётся paragraph. Многострочный plain-text paste/insertText использует ту же чистую планировку: одиночный LF — hard break, пустая строка — paragraph. Списки/цитаты/таблицы, пустые результирующие блоки и края Enter требуют последующих структурных инкрементов; это явный промежуточный отказ, не замена полного профиля v1. Три и более подряд LF при вставке отвергаются с сохранённым payload: повторные пустые строки нельзя молча схлопывать в один paragraph-разделитель.

Pure planner получает актуальный ParsedMarkdown/SourceSelection и действие, возвращает MarkdownPlan/ошибку formats. Он изменяет один исходный блок либо два соединяемых paragraph с разделителем. Нормализация допустима только внутри этой области: обычная пунктуация экранируется, крайние видимые пробелы кодируются entities, чтобы новые строки не стали непреднамеренным списком/HTML/отступом; inline-стили восстанавливаются на обеих частях. Целые link/reference/image/inline-code переносятся дословно, split внутри их скрытых маркеров/содержимого пока отклоняется; HTML/footnote/opaque не затрагиваются. Проверяется фактический AST результата: типы/число блоков и видимый текст не должны измениться из-за delimiter-run или reference-зависимостей.

Visual преобразует клавиши/clipboard в этот planner до изменения DOM, применяет одну исходную транзакцию с groupId=null и восстанавливает каретку по новой карте. IME не перехватывается как структурная команда. Code-block сохраняет прежний буквальный Enter/paste (без заявления о готовности fence-перепланирования); остальные контейнеры не меняются молча. Отказ Enter/paste сохраняет точный payload, блокирует дальнейшее изменение неподтверждённого ввода и переходы до явного discard; Backspace/Delete-отказ не создаёт текстовый payload. Проверки: MV-05 и отказ MV-16 через planner/core, Unicode/entities/CRLF/inline/защищённые соседи, единая undo/redo, DOM-клавиши и байты save/reopen.
