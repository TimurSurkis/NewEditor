# Локальное хранение и восстанавливаемое сохранение

Статус: **P4.1–P4.6 завершены на Linux x64; файловый IPC/UI подключены в P5.1–P5.4; восстановление UI и проверки остальных ОС остаются P7/P8**.
Редакция: 2026-11-26.
Основания: [архитектура](spec-architecture.md), [модель документа](spec-document-model.md), [контракты портов и IPC](spec-module-contracts.md), [план](../trackers/plan-desktop-v1.md).

Обновление 2026-11-26: [P5.4](spec-desktop-ui.md) подключает наблюдение/focus-refresh к окну, проверяет полномочия resource:watch/unwatch и ID подписки (часть LP-13 о runtime-подписках). Исторические результаты P4 ниже описывают состояние того этапа; выдача восстановленного ref и интерфейс восстановления по-прежнему относятся к P7.

Этот документ задаёт поведение, а не подтверждает готовность файлового редактора. Фактические проверки и текущая задача находятся в плане.

## 1. Границы и размещение

- Реализация находится в `src/platform/desktop/main/`: кодек, файловый реестр, чтение, очередь записи, SQLite-репозитории и наблюдатель. Сценарии приложения не получают пути, SQL или объекты Node.js.
- `DocumentStore`, `HistoryStore`, `DraftStore` и `ResourceEvents` реализуют действующие порты. Локальная аренда не нужна (`access: null`); ненулевой access отклоняется как `unsupported`.
- Файлы пользователя меняются только при явном сохранении. Загрузка может создать запись реестра и исходную версию в служебной SQLite, но не меняет пользовательский файл.
- Основной файловый UI/диалоги подключаются в P5; восстановление сессий и расписание черновиков — P7. В P4 проверяются сами адаптеры. Вложения и перенос относительных ссылок при Save As — P6.
- Недоступная/повреждённая служебная БД не заменяется пустой. Операции, которым нужны недоступные или непроверяемые данные, отклоняются с ошибкой; данные сохраняются для диагностики/восстановления. Нарушенная схема/ошибка стартового чтения pending-журнала блокирует весь адаптер. Полного сканирования всех завершённых записей при старте нет: повреждённый завершённый результат отклоняется при обращении и не считается missing/разрешением повторить запись.

## 2. Ресурс, путь и идентичность

### 2.1. Реестр и разрешения

`storageId` локального адаптера — `local`. `resourceId` — случайный UUID записи реестра, не путь и не хеш текста. Реестр хранится в профиле приложения; перенос файла между профилями не переносит автоматически его историю.

Только main регистрирует путь из файлового диалога, ассоциации файлов, второго запуска или проверенного восстановления сессии. Регистрация возвращает `StorageRef`. Разрешение использовать ref выдаётся конкретному WebContents; знание сохранённого UUID не даёт renderer доступ к произвольному файлу. Права на историю и цели сохранения проверяются той же границей IPC. После уничтожения WebContents его разрешения и подписки освобождаются. Незавершённые операции продолжают принадлежать main, а не окну.

Для существующего файла используется абсолютный `realpath`; для отсутствующей цели — `realpath` существующего родительского каталога и последнее имя. Регистрировать отсутствующие родительские каталоги и автоматически создавать их нельзя. Пустой путь, NUL, неподдерживаемое расширение и не обычный файл отклоняются. TXT: `.txt`; Markdown: `.md` и `.markdown`, без учёта регистра расширения. Неизвестный формат требует отдельного решения UI, а не угадывается по содержимому.

Ключ пути не подвергается Unicode-нормализации или безусловному lowercase. Для существующих путей `realpath` и проверка файловой идентичности объединяют обнаруженные алиасы; на нечувствительной к регистру файловой системе повторная регистрация не должна выдавать второй записываемый ресурс. Для ещё отсутствующих алиасов повторное разрешение перед записью обязательно. Если адаптер не может надёжно различить/объединить алиасы платформы, он возвращает `busy`/`unsupported`, а не запускает параллельные записи.

Символическая ссылка при выборе разрешается в конечный обычный файл: сохраняется он, а не текст ссылки. При каждой операции путь проверяется заново; изменение цепочки каталогов/ссылок не даёт права следовать к новой цели. Сам канонический путь не может оказаться символьной ссылкой. Чтение hard link допустимо; запись в файл с `nlink > 1` в v1 возвращает `unsupported`: атомарная замена иначе молча разорвала бы связь. Каталоги, устройства, сокеты и FIFO не читаются как документы. Ограничения Windows reparse points/ACL проверяются отдельно на Windows, не считаются доказанными Linux-тестами.

### 2.2. Документ и «Сохранить как»

- `DocumentId` — идентичность рабочей линии документа, `resourceId` — конкретного места хранения. Они не взаимозаменяемы. Несколько ресурсов могут быть связаны с одним DocumentId.
- Для впервые открытого внешнего файла реестр создаёт DocumentId. Замена содержимого по тому же пути сохраняет resourceId; inode не используется как постоянный ID. Удаление не стирает реестр, историю и черновики.
- Переименование внешней программой не переносит историю автоматически: старый путь становится отсутствующим, новый регистрируется отдельно. Автопоиск по совпавшему тексту запрещён.
- Save As сохраняет текущий DocumentId и весь точный снимок в новую цель. После подтверждения сессия связывается с новой целью. Старый файл, его история и реестр не меняются.
- История привязана к ресурсу, не копируется со старой цели. У новой цели начинается собственная история; при подтверждённой перезаписи существующей цели сначала сохраняется её прежний снимок. Её resourceId остаётся прежним, связь с DocumentId обновляется после записи.
- Save As в тот же канонический ресурс — обычное сохранение. Цель другой открытой сессии отклоняется приложением как `busy`. Main дополнительно сериализует записи по канонической цели, включая обнаруженные алиасы и разные окна.
- Отмена диалога ничего не создаёт. `expectedRevision: null` разрешает только создание отсутствующего файла. Подтверждение перезаписи существующей цели возвращает её фактическую ревизию; любая последующая смена ревизии требует нового решения пользователя.
- Пока нет P6, адаптер не заявляет перенос изображений или исправление относительных ссылок при Save As Markdown.

### 2.3. Фабрика и разрешения клиента P4.2

Фабрика `createLocalServices` создаётся **один раз для соединения/профиля в main**. Она владеет реестром, очередью по resourceId и клиентами-владельцами разрешений. `createClient(owner)` получает непрозрачный объект-владелец (в интеграции — WebContents); повторный вызов для живого владельца возвращает тот же клиент. Клиент предоставляет main-only `registerPath(path, 'open' | 'save-target')`, полный `documents` (load/save/getOperation/reconcile), `history.list/read` и `close`. Прежний модуль/имя `createLocalReadServices` сохранён как совместимый re-export; промежуточный Pick был расширен только вместе с журналом, без временного save в обход защиты.

Регистрация вызывается только после подтверждённого выбора пути в main. Для open ресурс должен существовать; save-target может отсутствовать, но родитель должен существовать. Регистрация резервирует ref/DocumentId в реестре без записи файла и без истории; поэтому неудачное дальнейшее чтение может оставить невыданные другим окнам служебные строки, но не ложную версию. Первое успешное load в одной транзакции добавляет исходную историю и привязывает проверенные encoding/BOM/hash/ревизию. При ошибке вся эта транзакция откатывается, снимок не выдаётся. Смена внешнего содержимого при последующих load обновляет метаданные чтения, но не добавляет версию.

Обнаруженные символьные и регистровые алиасы существующего файла используют прежний ref. Разные hard-link пути с nlink > 1 могут иметь разные ref для чтения; запись таких файлов по-прежнему запрещена. Не используем совпадение inode с исчезнувшим старым путём как основание переноса истории. До записи отсутствующих/неоднозначных алиасов потребуется повторная сверка из раздела 7.

Очередь регистрации общая (для однозначного создания ref), чтения и запросы истории сериализуются по ресурсу; независимые ресурсы не ждут друг друга. Ошибка задачи не отравляет следующую задачу, освободившиеся очереди удаляются. ref копируется до первого await. `close` немедленно отзывает все выданные этому клиенту права; уже ожидающее/выполняемое чтение повторно проверяет владельца перед фиксацией SQLite и выдачей снимка. Повторно созданный клиент того же владельца не наследует старые права. UUID, оставшийся в БД после перезапуска, сам по себе не является разрешением.

Все операции ждут `ready` стартового восстановления. При оставшейся незавершённой операции журнала load возвращает busy **до изменения метаданных/исходной истории**, а не скрыто завершает её. Чтение уже существующей истории не требует существования файла. getOperation не ждёт текущую очередь записи и может сообщить pending; reconcile входит в очередь ресурса/записи. Текущий preload/IPC не расширяется main-only методами регистрации или SQL.

## 3. Кодировки и точное представление

### 3.1. Чтение

Снимок сохраняет точные LF/CRLF/CR, табуляции, пробелы, наличие/отсутствие последнего перевода строки и NFC/NFD. BOM в начале файла представлен метаданными; только один начальный UTF-8 BOM снимается с текста при автоматическом определении. Остальные U+FEFF остаются обычным содержимым.

Порядок автоматического определения без достоверных сведений реестра:

1. BOM UTF-16/UTF-32 → `unsupported`, без попытки прочесть файл как Windows-1251.
2. UTF-8 BOM → строгое UTF-8-декодирование остатка; повреждённый UTF-8 → `encoding-error`, без fallback.
3. Без BOM: строгое UTF-8; при неуспехе — Windows-1251 с побайтовым round-trip. Неопределённый байт `0x98` не заменяется молча на U+FFFD.
4. NUL в тексте → `unsupported` (в v1 это не текстовый документ). Не вводим эвристик языка или автоматической Unicode-нормализации.

ASCII без подсказки читается как UTF-8. Автоопределение не доказывает исходную кодировку: некоторые Windows-1251-байты одновременно являются корректным UTF-8. UI P5 показывает выбранную кодировку; явное переоткрытие с иной кодировкой требует отдельного main-метода/расширения контракта перед реализацией, а не скрытого параметра текущего load.

Реестр хранит подтверждённые encoding/BOM вместе с SHA-256 точных байтов. Если байты совпадают, загрузка использует эти метаданные и проверяет обратное кодирование. Это сохраняет явно выбранную Windows-1251 у ASCII и обычный U+FEFF в начале текста UTF-8 без BOM. При других байтах подсказка больше не достоверна и применяется автоопределение. Сам UTF-8 BOM без реестра неоднозначен с обычным начальным U+FEFF; перенос файла в другую программу не сохраняет эту метаинформацию.

### 3.2. Кодирование

Новые документы — UTF-8 без BOM. Адаптер получает готовый `DocumentSnapshot`, не выбирает другую кодировку самостоятельно и не преобразует переводы строк. UTF-8 допускает BOM по метаданным; Windows-1251 с BOM недопустима. Непарный суррогат, NUL и непредставимый символ отклоняются до журнала/создания временного файла. Для Windows-1251 требуется точное равенство `decode(encode(text)) === text`, без подстановки `?` и транслитерации. U+FFFD не считается доказательством ошибки сам по себе: это может быть намеренный символ UTF-8-текста.

Используется `iconv-lite` **0.7.3** (актуальная версия сверена с npm 2026-11-25) с отключённым неявным удалением BOM; UTF-8 проверяется fatal-декодером. Версия прямой зависимости фиксируется в package.json и lockfile при подключении. Типы и runtime принадлежат адаптеру, не ядру.

Проверка кодека выявила особенность iconv-lite 0.7.3: неопределённый байт Windows-1251 `0x98` отображается в U+FFFD и обратно, поэтому один round-trip ошибочно считал бы его допустимым. В адаптере дополнительно запрещён этот байт в CP1251 и U+FFFD при CP1251-кодировании. Намеренный U+FFFD в UTF-8 разрешён.

## 4. Согласованное чтение и ревизия файла

Нельзя полагаться только на mtime или длину. Внутренняя файловая отметка включает SHA-256 всех байтов, размер, `dev`, `ino`, `mtimeNs`, `ctimeNs`, режим и nlink. Публичная `StorageRevision` — версионированный хеш сериализованной отметки; клиент проверяет только равенство. Отсутствие файла представлено null, не специальной строкой.

Чтение выполняется через один открытый descriptor обычного файла: fstat до чтения, все байты, fstat после, затем сверка текущего пути с descriptor. Изменение отметки, несовпадение длины/путевого состояния или обнаруженная подмена во время чтения дают `busy`; частичный LoadedDocument не возвращается. Где доступно, применяются no-follow/non-blocking flags, чтобы подмена обычного файла ссылкой/FIFO не приводила к следованию ссылке/зависанию. Это не защита от привилегированного злоумышленника или нестандартной файловой системы.

Одинаковый текст с изменённым BOM, inode, timestamp или правами получает другую ревизию; это безопасный лишний конфликт вместо незаметной подмены. Внешнее изменение «A → B → A» может быть обнаружено по ctime, но не обещаем отслеживать каждое промежуточное состояние. Одновременное чтение не является системным снимком ФС; обнаруженные гонки отклоняются, а локальная ревизия не выдаётся за атомарный compare-and-write.

## 5. SQLite и миграция v2

Сохраняем `service.sqlite` из P1 и `schema_migrations`; новая миграция `2 / local-persistence` выполняется одной транзакцией. `PRAGMA user_version` повышается только после всей миграции. Режимы: WAL, foreign_keys ON, busy_timeout 5000, **synchronous FULL** для журнала и черновиков. Более новая/некорректная схема отвергается без сброса. Миграция v1 не удаляется; новая база последовательно проходит v1 и v2. TEMP health_probe остаётся только диагностикой.

Схема ниже — обязательные поля и ограничения реализации; SQL находится в миграции, не в портах. JSON — стабильные plain DTO с явной версией внутреннего формата. При чтении JSON проверяется, а не приводится к TypeScript через один `as`.

| Таблица | Поля и ограничения |
| --- | --- |
| `local_resources` | `resource_id TEXT PRIMARY KEY`, `canonical_path TEXT NOT NULL UNIQUE`, `document_id TEXT NOT NULL`, `format TEXT CHECK IN ('txt','markdown')`, `representation_json TEXT NULL`, `content_hash TEXT NULL`, `last_revision TEXT NULL`, `next_version INTEGER NOT NULL CHECK > 0`, `created_at INTEGER NOT NULL` |
| `saved_versions` | `version_id TEXT PRIMARY KEY`, `resource_id TEXT NOT NULL REFERENCES local_resources`, `sequence INTEGER NOT NULL CHECK > 0`, `saved_at INTEGER NOT NULL`, `origin TEXT CHECK IN ('initial','before-overwrite','save')`, `snapshot_json TEXT NOT NULL`, `content_hash TEXT NOT NULL`, `UNIQUE(resource_id, sequence)` |
| `save_operations` | `operation_id TEXT PRIMARY KEY`, `resource_id TEXT NOT NULL REFERENCES local_resources`, `request_json TEXT NOT NULL`, `request_hash TEXT NOT NULL`, `phase TEXT CHECK IN ('prepared','replacing','file-written','settled','needs-attention')`, `old_revision TEXT NULL`, `old_snapshot_json TEXT NULL`, `new_content_hash TEXT NOT NULL`, `temp_name TEXT NULL`, `receipt_json TEXT NULL`, `outcome_json TEXT NULL`, `created_at INTEGER NOT NULL` |
| `draft_records` | `document_id TEXT NOT NULL`, `session_id TEXT NOT NULL`, `state_revision INTEGER NOT NULL CHECK >= 0`, `record_json TEXT NOT NULL`, `PRIMARY KEY(document_id, session_id)` |
| `draft_clearance` | `document_id TEXT NOT NULL`, `session_id TEXT NOT NULL`, `through_revision INTEGER NOT NULL CHECK >= 0`, `PRIMARY KEY(document_id, session_id)` |

Индексы: история по `(resource_id, sequence DESC)`; незавершённые операции по `(resource_id, phase)`. Частичный уникальный индекс допускает не более одной операции ресурса с phase != settled. DocumentId в `local_resources` не UNIQUE: Save As сохраняет линию документа в нескольких местах. История не ссылается на текущий DocumentId, а черновики нового документа не требуют resourceId. FK не используют каскадное удаление пользовательских данных.

`request_json` содержит полный неизменяемый SaveRequest; hash считается по каноническому порядку значимых полей, а не порядку свойств входного объекта. `old_snapshot_json` нужен для сохранения заменяемого содержимого, новый снимок уже находится в request. `temp_name` — только сгенерированное имя рядом с целевым файлом, не пользовательский путь. Реализация проверяет принадлежность временного файла операции до очистки.

Завершённые результаты операций и tombstone-границы черновиков в P4 не удаляются по возрасту: иначе поздний повтор мог бы записать файл снова/воскресить черновик. Лимит **пяти** применяется только к `saved_versions`, не к операциям/черновикам. Это осознанный рост служебной базы; политику безопасной компактизации можно ввести отдельной спецификацией, не ослабляя идемпотентность.

### 5.1. Доступ репозиториев и проверка JSON

`ServiceDatabase.connection` — main-only соединение, открытое с проверенной схемой и параметрами. Его используют платформенные репозитории; закрывает только ServiceDatabase. Это не метод preload и не разрешение UI выполнять SQL. В P4.2 версия схемы остаётся 2: дополнительных таблиц не требуется.

`representation_json` записывается как `{ "version": 1, "fileMetadata": ... }`, `snapshot_json` — `{ "version": 1, "snapshot": ... }`. Чтение проверяет версию, типы, Unicode, совместимость encoding/BOM, безопасные целые sequence/время и hash точных закодированных байтов снимка. Неподходящий JSON/неизвестная версия/несовпавший hash дают io-error, не пустую историю и не перезапись повреждённой записи. Операции первоначальной версии, счётчика и метаданных чтения выполняются одной короткой синхронной транзакцией.

### 5.2. Приватность служебных файлов P4.6

Профиль содержит полные тексты истории, черновиков и журнала, поэтому стандартного umask недостаточно. Main подготавливает выделенный userData-каталог до открытия БД: на POSIX он принадлежит текущему пользователю и имеет mode 0700. Более широкие права существующего **выделенного профиля** сужаются, но права его родительских каталогов не меняются. Последний компонент профиля не может быть символьной ссылкой; системные алиасы родительских каталогов допускаются. Каталог создаётся без изменения глобального process.umask.

`openServiceDatabase` требует уже существующий приватный родительский каталог. Файл БД при отсутствии предварительно создаётся exclusive с mode 0600; существующая БД и sidecars (`-wal`, `-shm`, `-journal`) проверяются до открытия SQLite. На POSIX принимаются только обычные файлы текущего uid с nlink=1, их права сужаются до 0600; ссылка/чужой владелец/hard link/необычный тип отклоняются без удаления или перезаписи. После включения WAL/миграций права созданных sidecars проверяются повторно. Ошибка приватности показывается как недоступная служебная БД, не обходится созданием другой пустой БД. Схема не меняется.

На Windows POSIX mode/uid не доказывают корректность DACL: приложение использует выделенный системный userData, не обещает перенос произвольного ACL. Проверки reparse points/DACL и системного профиля Windows остаются в P8. На POSIX приватность защищает от других непривилегированных пользователей, но не от root или вредоносного процесса того же пользователя. Служебные тексты не шифруются. Сужение прав старого профиля не отменяет возможное предыдущее раскрытие его данных.

## 6. История

1. Первое успешное открытие существующего файла сохраняет его точный начальный снимок (`origin: initial`) в одной транзакции с регистрацией/привязкой метаданных. Если SQLite не принимает запись, load не выдаёт успешный документ с обещанной историей. Исходный файл при этом не меняется.
2. Повторное открытие не создаёт новую версию. Внешнее редактирование само по себе не пополняет историю редактора.
3. Перед перезаписью сохраняется фактический прежний снимок цели, если он отличается от последней версии, затем записанный снимок. Поэтому новая внешняя редакция/содержимое существующей цели Save As не теряются молча при первом нашем сохранении. Это выполняется вместе с завершением журнала; ошибка до записи оставляет историю прежней.
4. При отсутствии изменения снимка нет нового временного файла и новой версии. Если ранее не было истории существующего файла, его снимок регистрируется как исходный. Новый пустой файл всё равно создаётся и получает первую версию.
5. Дедупликация — только относительно последнего состояния, не всех пяти. Последовательность A → B → A содержит три события сохранения. Изменение только кодировки/BOM является новым состоянием даже при одинаковом тексте/одинаковых ASCII-байтах.
6. Транзакция завершения добавляет недостающие состояния и оставляет пять последних по sequence, включая подтверждённое последнее. Время не используется для порядка: часы могут идти назад. VersionId случайный, не StorageRevision.
7. `list` сортирует от новой к старой; `read` возвращает точный снимок без записи файла. История известного ресурса доступна и после удаления исходного файла. Восстановление снимка в сессию — обычная отменяемая правка; восстановленный снимок не считается сохранённым до явного save.
8. Неподдерживаемую/нечитаемую существующую цель нельзя молча заменить с обещанием истории: возвращается ошибка до записи. Неподдерживаемый файл пользователь может обработать другой программой или выбрать иную цель.

## 7. Очередь и протокол сохранения

Детализация реализации P4.2/P4.3:

- Полная фабрика называется `createLocalServices`; прежнее имя читающей фабрики остаётся совместимым re-export. Клиент получает полный DocumentStore. `ready` — main-only результат стартового восстановления; операции клиента ждут его. Незавершённый неизвестный исход блокирует только свой ресурс; ошибка проверки pending-журнала при старте/недоступная БД — весь адаптер. Production composition/IPC подключаются в P5, поэтому готовность фабрики не означает готового файлового UI.
- Для минимальной защиты от ещё не объединённых алиасов **файловые записи/reconcile последовательно проходят общую очередь записи**, дополнительно к очереди ресурса. Чтения независимых ресурсов не блокируются этой очередью. Перед записью проверяются канонический родитель, обычный файл, hard link, права и обнаруженные дубликаты реестра; неоднозначность даёт busy, не вторую параллельную запись.
- SaveRequest копируется и проверяется до первого await; fingerprint задаётся фиксированным порядком значимых полей. Формат/DocumentId целевого ресурса после сохранения берутся из запроса. Закрытие владельца до принятия запроса в prepared отменяет принятие; после prepared main доводит уже принятую запись независимо от окна. Проверка прав требуется и при чтении результата/reconcile после переоткрытия.
- `request_json` имеет внутреннюю оболочку `{ version: 1, request, tempIdentity }`. Сам request неизменяем; tempIdentity первоначально null, после подготовки содержит строковые dev/ino созданного temp. Это не требует смены схемы v2. Имя temp — отдельный случайный UUID, не пользовательский operationId. При EEXIST чужой temp не удаляется. После сбоя до фиксации identity принадлежность не доказана: файл оставляется, а не удаляется по одному имени/hash. Возможный служебный orphan — ограничение, не основание рисковать чужим файлом.
- Очистка temp проверяет канонического родителя, обычный файл и сохранённые dev/ino. При ненадёжном inode безопасная запись не обещается (unsupported). POSIX mode/uid/gid переносятся через descriptor temp; read-only исходник нельзя обойти правом на каталог. Поддержка произвольных ACL/xattr не заявляется; остальные ОС требуют отдельных проверок.
- Непосредственно перед публикацией повторно проверяются descriptor/имя temp, dev/ino, nlink и SHA-256 его байтов; обнаруженная подмена не публикуется. Старый снимок в old_snapshot_json также имеет собственный contentHash. Эти проверки обнаруживают гонки, но не превращают Node rename/link в атомарный compare-and-write с несотрудничающей внешней программой.
- Temp/replace пропускаются только для полного no-op: совпадают снимок, DocumentId и формат цели. При изменении encoding (даже ASCII с теми же байтами) или связи Save As выполняется публикация temp: новый inode/файловая ревизия не позволяет другой сессии молча затереть более новые метаданные со старой expectedRevision. Это намеренный выбор вместо отдельной логической ревизии в SQLite. Обычный no-op не создаёт новую версию; новый пустой документ создаёт файл.
- Низкоуровневая публикация возвращает отдельные результаты «опубликовано», «цель уже появилась», «достоверно не опубликовано». Исключение после начала публикации трактуется как unknown: обёртка/транспорт могли потерять ответ уже после rename/link. Такой результат нельзя превращать в not-written по одному коду исключения.
- После подтверждения записанных байтов сначала отдельно сохраняется file-written/receipt, затем атомарно завершаются история/метаданные/settled. До завершения истории receipt.versionId может быть null (версия ещё не подтверждена); финальный saved возвращает фактический ID новой версии или null при отсутствии новой версии. Ошибка фиксации file-written при достоверной receipt также остаётся history-pending; после потери процесса её придётся выяснять по replacing и файлу.
- Штатное создание отсутствующей цели публикует готовый temp через link без перезаписи, затем убирает собственное временное имя. Ошибка fsync каталога после публикации не означает, что файл не записан. Известные неподдерживаемые directory-fsync операции допускаются как ограничение ОС/ФС; неожиданный сбой оставляет unknown. Проверка переживания отключения питания для всех ФС не заявляется.
- История и завершённый исход операции фиксируются одной транзакцией. Перед новым снимком добавляется недостающий прежний снимок, затем новый; дедупликация только соседняя и учитывает encoding/BOM. Остаются пять последних записей по sequence. Черновики DocumentStore не очищает: это делает приложение по capturedStateRevision.

### 7.1. Валидация и подготовка

Все обращения одного main к ресурсу сериализуются. Очередь ресурса включает load/сверку, save и reconcile; операции SQLite выполняются короткими синхронными транзакциями без `await` внутри. Очередь не должна блокировать ввод renderer.

1. Проверить runtime DTO, разрешения, storageId/access, format/ref, Unicode/метаданные и представимость текста. Вход копируется до первого await. Неверный DTO → `not-written/invalid-input`, ошибка представимости → `not-written/encoding-error`.
2. По operationId найти ранее принятый запрос. Тот же ID с другим полным payload → `not-written/invalid-input`, без изменения прежней операции. Тот же payload возвращает сохранённый исход или продолжает reconcile; проверка новой ревизии не должна превратить уже выполненный повтор в конфликт.
3. До новой операции завершить/разрешить прежнюю незавершённую операцию ресурса. `needs-attention` блокирует автоматические новые записи как `busy`. Иная цель Save As остаётся доступна.
4. Согласованно прочитать цель и сравнить expectedRevision (включая отсутствие). При несовпадении вернуть/сохранить `conflict`. Существующую цель декодировать и проверить права/тип/hard link до записи. Разрешение каталога не заменяет проверку записываемости существующего файла: атомарная замена не должна обходить read-only файл.
5. В одной SQLite-транзакции создать `prepared` с исходной ревизией/снимком, полным новым запросом, hash байтов и зарезервированным именем temp. При неуспехе известно, что файл не записан.

### 7.2. Файловая операция

1. Создать соседний temp через exclusive create (`wx`, исходно mode 0600); нельзя переиспользовать произвольный найденный temp. Записать все байты, применить допустимые POSIX-права исходного файла без setuid/setgid и вызвать fsync descriptor. Для нового файла остаются приватные права. Права/ACL Windows проверяются отдельно; обещания сохранения произвольных xattr/ACL пока нет. Если требуемые для безопасной записи права сохранить нельзя, вернуть ошибку до замены.
2. Ещё раз прочитать/сверить цель и канонический путь с исходной ревизией. При конфликте temp удаляется только как собственный файл, операция завершается конфликтом, целевой файл не меняется.
3. До попытки изменения цели зафиксировать phase `replacing`. Если эта SQLite-запись не удалась, целевой файл не меняется.
4. Существующий файл заменить `rename` соседнего temp без предварительного unlink цели. На платформах с ошибкой замены занятых/read-only файлов вернуть ошибку, не удалять цель для обхода отказа. Отсутствующую цель создать без перезаписи через exclusive publication (например, link готового temp → цель и удаление temp); если ФС не даёт такой гарантии, `unsupported`, не небезопасный fallback на rename поверх неожиданно появившегося файла.
5. По возможности fsync родительского каталога; неподдерживаемая ОС/ФС фиксируется в матрице гарантий. Повторно получить ревизию результата и убедиться в совпадении записанных байтов. Неизвестный исход после начала замены → `unknown`, а не «не записано».
6. В одной SQLite-транзакции записать receipt/`file-written`, добавить историю, обновить связь ресурса/метаданные, применить лимит и завершить `settled/saved`. Новая versionId выдаётся только если возникла новая версия; no-op может вернуть null.

Отдельная фаза `file-written` может быть подтверждена перед транзакцией истории, если финальная фиксация истории не удаётся. При достоверно записанном снимке возвращается `history-pending` с receipt и новой ревизией. При невозможности достоверно подтвердить запись/receipt возвращается `unknown`; журнал уже содержит новый снимок. Нельзя вернуть `not-written` только потому, что упала последняя SQLite-транзакция.

### 7.3. Идемпотентность и пределы атомарности

`saved` означает файл + историю; `history-pending` — файл подтверждён, история не закончена. `getOperation` читает состояние без файловой записи: settled возвращает сохранённый исход; file-written с receipt — `history-pending`; prepared/replacing/needs-attention — pending. Отсутствующий ID — missing. `reconcile` отсутствующего ID возвращает unknown/not-found; приложение может повторить только исходный запрос с тем же ID и expectedRevision.

Конфликт/известный отказ до замены фиксируются как settled, когда БД доступна; повтор не переоценивает тот же operationId по новым условиям. Если запрос не удалось зарегистрировать из-за отказа БД, getOperation может вернуть missing. Новый пользовательский снимок/новая попытка после известного отказа получает новый ID. Повтор истории с тем же ID не добавляет вторую версию и не обрезает новые версии повторно.

ФС и SQLite не являются общей транзакцией. Произвольная внешняя программа может изменить файл между последней проверкой и rename: атомарный локальный compare-and-write не обещается. Предварительная проверка и наблюдатель уменьшают окно, но не отменяют его. Не обещается переживание физической поломки носителя; гарантии fsync/rename/каталогов и замены открытых файлов проверяются по каждой ОС. Linux-проверки не закрывают macOS/Windows.

## 8. Восстановление журнала

До обслуживания записей после запуска main сканирует незавершённые операции. Восстановление **никогда не продолжает запись temp поверх пользовательского файла автоматически**. Наличие нового снимка в журнале ещё не означает, что пользовательский файл можно заменить.

| Состояние/фактический файл | Действие |
| --- | --- |
| prepared (замена ещё не начиналась) | Снять незавершённую попытку как not-written; удалить только принадлежащий операции temp. Рабочий снимок остаётся в журнале/черновике; новая запись — отдельное пользовательское действие |
| replacing, temp планировался и цель точно сохранила прежнюю ревизию | not-written, даже если старые и новые байты одинаковы: публикация метаданных/связи ещё не произошла. Эту проверку выполняем до совпадения нового hash |
| replacing, байты цели совпали с новым снимком | Получить актуальную ревизию, идемпотентно завершить историю/реестр и вернуть saved. Это доказывает наличие нужного состояния, но не авторство каждого внешнего действия |
| replacing, цель точно соответствует прежней ревизии (либо обе цели отсутствуют), новый снимок отличается | Зафиксировать not-written; temp не публиковать. Пользователь может сохранить снова |
| replacing, иное состояние/удаление/ошибка чтения | needs-attention, unknown; сохранить оба снимка/журнал, не трогать файл. Восстановление P7 предлагает сравнение/сохранение в другую цель |
| file-written с достоверным receipt | Зафиксировать именно подтверждённый снимок истории даже если позже файл изменён/удалён извне; не переписывать файл и не выдавать старую receipt-ревизию за актуальное внешнее состояние |
| Ошибка завершения SQLite при совпавшем новом снимке | history-pending с receipt, если он достоверен; иначе unknown. Снимок и незавершённая операция не удаляются |
| settled | Вернуть прежний исход; ни файл, ни история не меняются |

При несовпадении нового снимка нельзя считать старую операцию обычным конфликтом, если сама запись могла состояться: `conflict` подразумевал бы известное отсутствие нашей записи. Для такого случая сохраняются `unknown` и needs-attention. Автоматическое снятие блокировки неизвестной операции не входит в P4; явное разрешение после сохранения материалов восстановления описывается перед UI P7. Это ограничение не препятствует Save As в другой ресурс.

Если в `replacing` новый и старый снимки имеют одинаковые байты (например, ASCII со сменой encoding), один hash недостаточен. Запланированный temp и неизменная старая ревизия означают отсутствие публикации; изменившаяся ревизия при совпавших новых байтах позволяет завершить метаданные/историю. Сохранённые encoding/BOM берутся из запроса, а не повторного автоопределения. Полный no-op без temp может завершиться по совпадению текущего снимка.

Чужие temp не удаляются по маске. Журнал не очищается при закрытии окна, неудаче черновика или обычном открытии файла. Прерывание main после rename до SQLite — обязательная нативная проверка.

## 9. Черновики

`DraftRecord` хранится целиком, включая baseline, location, baseStorageRevision и сохраняемые метаданные. Ключ — DocumentId + SessionId, а не путь. Новый документ может не иметь location. Никакой записи исходного файла, истории или копирования вложений в `put` нет.

`put` и `removeThrough` выполняются транзакционно. Сначала проверяется `draft_clearance`; ревизия <= through не принимается. Далее более старая запись не принимается; равная с тем же полным DTO идемпотентна, с другим DTO — invalid-input; новая заменяет record. `removeThrough` увеличивает границу через max и удаляет только record с ревизией <= неё. Операция не удаляет черновики других сессий и не сбрасывает границу после удаления record. Повтор после перезапуска подчиняется тем же правилам.

Подтверждение save не переписывает уже зафиксированный DraftRecord той же stateRevision и не очищает более новый черновик. Условная очистка выполняется сценарием приложения, не безусловным DELETE внутри DocumentStore. Если очистка не удалась, сохранение файла не объявляется неудачным. Планирование 1 с покоя / максимум 5 с непрерывного ввода и восстановление UI — P7.

Детализация P4.5:

- `record_json` — `{ version: 1, record: DraftRecord }`. При чтении проверяются версия, все DTO-поля, безопасная stateRevision и соответствие колонкам ключа/ревизии. JSON канонизируется порядком полей, поэтому равная ревизия с переставленными свойствами остаётся идемпотентной. Повреждённая запись не заменяется/удаляется автоматически.
- Черновик **не проверяется кодеком файла**: emoji при выбранной Windows-1251 и NUL могут быть рабочим текстом до исправления ошибки сохранения. Требуются корректный Unicode и совместимые encoding/BOM, но представимость в файле — только при явном save. baseline сохраняется столь же точно.
- Клиент реализует StorageServices (`id: local`, документы/история/черновики/события; assets/access пока null). Первый put/removeThrough нового, отсутствующего и в records, и в clearance ключа связывает его с владельцем. Один ключ нельзя захватить другим активным клиентом. Закрытие отзывает доступ, но не удаляет запись или границу очистки.
- `drafts.list` показывает только ключи этого владельца. Для восстановления есть **main-only** `listRecoverableDrafts()` (без активных владельцев) и `client.recoverDraft(key)`, явно выдающий существующий ключ после пользовательского решения будущего P7. Один UUID/старый sessionId не разрешает другому renderer читать или менять сохранённый черновик. Публичного recovery-IPC до P7 нет.
- Ненулевая location должна быть уже выданным этому клиенту локальным ref. При явном восстановлении разрешено сохранять прежнюю location выбранного черновика без выдачи файлового доступа: это только сохранение ссылки в record, не право читать/писать исходный файл. Новая location требует обычного разрешения. Сценарий новой восстановленной SessionId и повторной выдачи файловых полномочий детализируется в P7.
- put/removeThrough не обращаются к файлам и не изменяют сохранённую историю. Транзакция clearance + условное удаление должна откатываться целиком при ошибке; более новый record остаётся. Ключи и payload фиксируются до первого await.

## 10. Наблюдение

Наблюдается родительский каталог, чтобы пережить атомарную замену inode; дополнительно используется проверка состояния не реже раза в 2 секунды и при возвращении фокуса. Системное событие — только повод проверить файл. События объединяются на 100 мс; сохранения и перечитывания проходят через ту же очередь ресурса.

Сравниваются проверенные ревизии, а не имена событий fs.watch. Собственная запись обновляет наблюдаемую ревизию **до** снятия очереди/доставки сохранения; совпавшая ревизия не выдаёт ложное changed. Иное внешнее состояние, обнаруженное после нашей записи, не подавляется по таймауту. Отсутствие даёт deleted один раз до следующего изменения. Чтение с busy повторяется; permission/io-error передаётся через onError, а не маскируется под удаление. Отписка и уничтожение renderer освобождают watcher, polling и незавершённую регистрацию.

Наблюдатель сообщает только ref/kind. Решение перечитать чистую сессию или показать конфликт принимает приложение с проверкой session/stateRevision/IME; неподтверждённый редакторский ввод не выбрасывается адаптером. Даже при неработающем наблюдателе save обязан проверить ревизию.

Детализация P4.5:

- Проверка наблюдателя использует общий **байтовый probe** (descriptor/stat/hash/канонический путь), без декодирования текста. Поэтому внешний неподдерживаемый текст тоже даёт changed; ошибка последующего load не теряет рабочую копию. FIFO/каталог/отказ доступа дают onError, не deleted.
- Одна запись ресурса разделяет watcher и polling между подписчиками; каждый подписчик имеет собственную последнюю известную ревизию. Она берётся из последнего успешного load/подтверждённой записи **его владельца**, а не из глобальной записи реестра: чужой save между load и watch не должен потеряться. При отсутствии известного снимка первая проверка только устанавливает исходное состояние, без искусственного deleted.
- Подтверждение свежих записанных байтов обновляет ревизию только у владельца принятой операции и только до освобождения очереди ресурса. Другие владельцы получают changed. Повтор cached receipt и завершение file-written-истории без чтения текущего файла не откатывают наблюдаемую ревизию к старому состоянию.
- При replacing/потерянном ответе собственный результат с совпавшим новым hash временно не выдаётся владельцу как внешнее изменение до reconcile. Иной hash/удаление и needs-attention не подавляются. Сам наблюдатель не изменяет журнал и не делает скрытый reconcile.
- Повторные сигналы объединяются одним 100-мс таймером; одновременно не более одной проверки ресурса и одного повторного намерения. Polling 2000 мс обходит ожидание debounce. При busy проверка повторяется; watcher-ошибка сообщает onError, polling остаётся и пробует восстановить watcher. Listener/onError не могут исключением отравить очередь или других подписчиков.
- Наблюдение запускается только после ready и проверки прав; немедленная отписка отменяет ещё не начатую регистрацию. Последняя отписка закрывает watcher/timers; закрытие клиента отзывает все его подписки, в том числе ожидающие. `LocalServices.close()` освобождает клиентов/наблюдение; уже принятые сохранения он не отменяет, перед закрытием SQLite main должен дождаться принятых операций.
- Main-only `client.refreshResources()` инициирует проверку его наблюдаемых ресурсов при возвращении фокуса. Связь с WebContents/IPC/focus-событиями — P5; автоматического перечитывания UI или расписания черновиков в P4.5 нет.

## 11. Ошибки

| Ситуация | Результат до изменения цели |
| --- | --- |
| Чужой/невыданный ресурс, отказ доступа ОС | permission-denied |
| Отсутствующий известный файл | not-found при load; conflict/null при несовпадении expectedRevision save |
| Некорректный DTO/operationId payload/BOM | invalid-input |
| Невалидная поддерживаемая кодировка/непредставимый символ | encoding-error |
| Неподдерживаемый формат/тип файла/NUL/hard-link запись/безопасная публикация недоступна | unsupported |
| Файл менялся во время чтения, занятая цель, незавершённый журнал | busy |
| Остальные ошибки ФС/SQLite, включая ENOSPC | io-error |

`retryable` означает техническую возможность повтора после устранения причины, не автоматический повтор с новой ревизией. Текст ошибки не содержит stack trace, SQL или лишние пути чужих файлов. После начала изменения цели эти же ошибки классифицируются с учётом известного исхода: not-written, history-pending или unknown.

## 12. Критерии проверки P4

| ID | Проверка |
| --- | --- |
| LP-01 | UTF-8 с/без BOM, Windows-1251, ASCII, emoji, NFC/NFD, смешанные LF/CRLF/CR и крайний U+FEFF проходят точный round-trip; неподдерживаемая кодировка/NUL/0x98/непарный суррогат/непредставимый символ дают отказ без потери байтов |
| LP-02 | Неподвижный файл читается с согласованной ревизией; изменение той же длины при сохранённом mtime меняет ревизию; inode-замена тоже обнаруживается |
| LP-03 | Повтор/алиас пути даёт тот же ресурс; подмена ссылкой/каталогом/FIFO не приводит к записи/зависанию; hard-link запись не разрывает связь |
| LP-04 | Миграция v1 → v2, новая база, повторное открытие, rollback сбоя миграции, более новая схема, FK/уникальные ограничения и synchronous FULL проверены нативным Electron |
| LP-05 | Один общий load/save-набор проходит memory/local; null expectedRevision не перезаписывает появившийся файл, старая ревизия конфликтует |
| LP-06 | Начальный снимок существующего файла есть в истории; no-op не дублируется; ASCII encoding-only и A → B → A создают версии; после 6+ сохранений остаётся ровно 5 |
| LP-07 | Save As сохраняет DocumentId, не меняет старую цель/её историю, сохраняет прежнее содержимое подтверждённой существующей цели; отмена не создаёт файл |
| LP-08 | Повтор operationId до/после перезапуска не пишет файл/версию снова; иной payload отклоняется; две записи одной цели не обгоняют друг друга |
| LP-09 | Ошибки кодека/prepare/temp/fsync/повторной проверки/replace/финальной SQLite различаются; оригинал не удаляется для обхода ошибки замены; материалы восстановления не теряются |
| LP-10 | Прерывание процесса на границах prepared/replacing/rename/receipt/history восстанавливается по таблице раздела 8; неизвестный внешний файл не перезаписывается автоматически |
| LP-11 | Сбой/повтор черновиков, монотонная очистка, поздний put, две сессии, новый документ, более новые правки во время save проверены через повторное открытие БД |
| LP-12 | Собственная запись не даёт ложный конфликт; внешние замена/изменение/удаление обнаруживаются; watcher/polling освобождаются; ошибки не превращаются в deleted |
| LP-13 | Runtime IPC отклоняет невыданный ref и чужую подписку; восстановленный ref выдаётся только проверенным main-сценарием |
| LP-14 | Профиль POSIX 0700, SQLite/WAL/SHM 0600 при umask 000; старые широкие права сужаются без изменения текстов, ссылки/hard links/необычные типы отклоняются без повреждения цели |

В P4.6 нативные проверки ФС/SQLite выполняются в runtime Electron, включая принудительное завершение дочернего процесса; fault injection находится в тестовых обёртках границ ввода/вывода, не в скрытых production IPC-командах. P5/P7 добавляют GUI-пути, P8 заполняет платформенную матрицу. До фактических результатов строки критериев не считаются выполненными.

Для нативных TypeScript-проверок реестра/репозиториев используется уже установленный Vite: SSR-бандл теста в игнорируемом `out/native-tests`, затем `node:test` внутри Electron в Node-режиме. Это позволяет проверять реальные модули с существующими barrel-импортами без новой библиотеки загрузчика TS. В тесте обязательно проверяется `process.versions.electron`; проверки обычного Vitest отдельно не обозначаются нативными.

В поставку включаются только `out/main`, `out/preload`, `out/renderer` и package.json. Общая маска `out/**` больше не используется: появление `out/native-tests` не должно добавлять тестовые сценарии в app.asar. Отсутствие тестового бандла проверяется после упаковки отдельно от GUI.

### 12.1. Приёмка P4.6

- Один неизменяемый набор сценариев load/save/history/drafts запускается для memory через Vitest и для local через node:test в Electron. Сравниваются точный снимок, expectedRevision/null, идемпотентность operationId, новый payload старого ID, Save As, пять состояний после явных сохранений и монотонная очистка черновиков. Конкретные UUID/ревизии/часы не сравниваются между реализациями.
- Memory не эмулирует файловый кодек, исходную историю seed, разрешения WebContents, журнал или watcher. Эти различия проверяются локальными наборами, а не маскируются условными пропусками общего контракта.
- Ревизия защищает также идентичность/формат сохранённого ресурса: Save As поверх другого документа с тем же снимком обновляет связь DocumentId и ревизию. Memory должен отражать эту общую гарантию, хотя в local она обеспечивается новой физической публикацией тех же байтов. Смена только идентичности без изменения снимка сама по себе не требует дубликата версии.
- Нативные сценарии DocumentApplication + local проверяют: новые правки/черновик во время старого save; history-pending/unknown и reconcile; ошибку очистки черновика при успешном save; чистое перечитывание и конфликт грязной сессии по событию; устаревшее асинхронное чтение. Подписка, вызывающая reload, подключается только тестом; файлового UI/IPC до P5 нет.
- Повторяются все существующие частичные отказы и семь настоящих SIGKILL, сборка/упаковка и GUI-регрессии. LP-13 на уровне нового файлового IPC остаётся P5, восстановление UI — P7, другие платформы/реальный ENOSPC/обрыв питания — P8; эти ограничения не обозначаются выполненными при закрытии Linux-подэтапа P4.
